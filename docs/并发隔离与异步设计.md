# 并发隔离与异步执行设计

> 目标：让助手在**多用户同时提问**时依然正确、可控。
> 本文回答三个问题：现状哪里会出事、怎么改、改完怎么证明它真的成立。

---

## 一、先说结论：现状有六个隐患，其中两个是致命的

多人同时跟助手说话，和一个人连点几次，是完全不同的两件事。前者会同时压到
**数据库连接、Web 容器线程、工具执行线程、以及共享的轮次状态**上。
逐一排查后确认的问题（前两个是致命级）：

| # | 隐患 | 现状 | 后果 |
|---|------|------|------|
| 1 | **事务跨越模型调用** | `AssistantService.sendDetailed` 挂 `@Transactional`，而方法体内有 1–6 次大模型调用 | 一轮对话从头到尾**独占一个数据库连接**十几秒。Hikari 池只有 12 → 第 13 个并发提问卡在等连接；更糟的是商城的下单/查商品/登录共用这个池，**助手慢会拖死整个站点** |
| 2 | **同步阻塞 Web 容器线程** | Controller 同步返回，模型调用期间 Tomcat 工作线程被占住干等 | 默认 200 个工作线程，几十个「等模型」的助手请求就能吃干净，之后连首页和静态资源都排不上队 |
| 3 | **轮次上下文是裸 ThreadLocal** | `PendingActionService.CURRENT_TURN` 静态 ThreadLocal；工具 worker 池化复用且从不清理 | 读到**别的用户遗留在同一线程上的值** → A 的支付卡片挂到 B 的会话里。当前靠 `@Effectful` 让写工具留在调用线程侥幸避开——是**约定，不是机制** |
| 4 | **同一会话没有串行** | 并发两条消息各自读到同一份历史快照，再各自追加 | 对话历史顺序错乱，模型看不到刚发的那条，表现为「答非所问」 |
| 5 | **只有频次限制，没有在途限制** | `AssistantRateLimiter` 管 20 次/分钟 | 挡不住「同一秒发 20 条、20 条同时在途」——资源瞬时打满 |
| 6 | **并行工具池全局共享且只有 4 线程** | 每个轮次 fan-out 最多 4 个只读工具，16 个并发轮次需要 64 条线程 | 实际只有 4 → 全部排队 → `allOf().get(timeout)` 集体超时 → **所有用户一起**拿到「查询超时」 |

第 3 条之所以危险，是因为它**不报错**：没有异常、没有日志，只是卡片出现在错误的地方
或者干脆不出现。这类静默失败靠人眼回归是发现不了的。

## 二、隔离：三层机制，各自解决一类串味

「隔离」在这套代码里不是一个抽象概念，而是三个具体的东西：

### 第 1 层：轮次上下文 `TurnScope`（解决「状态串味」）

`assistant/harness/TurnScope.java`，替代原来的裸 ThreadLocal。它把「本轮属于哪个会话、
哪个用户、产生了什么」收在一个显式的上下文里，并提供三条保证：

```java
try (TurnScope.Scope turn = TurnScope.begin(conversationId, username)) {
    // 本轮内：工具可以读到会话与用户（服务端注入，模型改不了）
    // 本轮产生的产物写进上下文属性，轮次结束时取出
}
// 退出即还原——不需要任何人记得清理
```

1. **清理是自动的，不是纪律**：用 `AutoCloseable` 表达「进入/退出」，
   try-with-resources 保证异常路径也会退出。原来的写法靠人工在 `finally` 里 `remove()`，
   多一条代码路径就可能漏一处。
2. **退出时「精确还原」而不是清空**：这一点很反直觉但很重要。worker 线程是池化复用的，
   进入时可能已经残留着上一个使用者的上下文。**清空同样是破坏性行为**——
   它把不属于你的状态弄丢了。正确做法是还原成「进入前的样子」。
3. **跨线程传播是单向快照**：`TurnScope.wrapRunnable(...)` 在提交任务前捕获快照，
   任务在自己线程上装载、执行、还原。所以并行执行的只读工具：
   - 读得到本轮的会话与用户（不会串味到别人身上，也不会像原来那样静默读到 `null`）；
   - 但它在快照副本上的写入**不会回流**到调用线程。

   第 3 条带来一个直接推论，也是 `@Effectful` 现在的技术理由：
   **需要产生产物的工具必须留在调用线程执行**，否则它写的属性只留在 worker 的快照里，
   主线程取不到——表现为「不报错但确认卡片不出现」。

### 第 2 层：并发闸门 `AssistantConcurrencyGate`（解决「资源争抢」）

频次限制（多少次/分钟）和在途限制（此刻多少条正在被处理）是两件事，必须都有。
闸门按成本从低到高依次开合：

| 闸门 | 默认值 | 拒绝时的响应 | 保护的东西 |
|------|--------|--------------|------------|
| 全局在途 | 16 | `503 ASSISTANT_BUSY` | 整个应用。满了就不该再放人进来，快速失败优于让所有人一起排到超时 |
| 每用户在途 | 3 | `429 TOO_MANY_IN_FLIGHT` | 防止一个人开多个会话把全局额度占光——最常见的「一人拖垮所有人」路径 |
| 会话串行 | 开 | `409 CONVERSATION_BUSY` | 不只是限流，更是**正确性**：同会话并发会让历史顺序错乱 |

拒绝时一律写审计（`stage=RATE`，规则 `CONCURRENCY_GLOBAL` / `CONCURRENCY_USER` /
`CONVERSATION_BUSY`），店员在审计面板看得见——「谁在被拒绝、为什么」是容量规划的依据。

> **实现上的取舍**：会话锁表与用户计数表「只增不减」。安全地移除一个仍可能被使用的条目
> 需要第二把锁加引用计数，收益只有几十字节。在并发路径上，正确性优先于微小的内存节省；
> 生产长期运行应换成带过期策略的本地缓存（Caffeine）或分布式锁（Redis）。

### 第 3 层：执行器物理隔离（解决「互相拖垮」）

助手线程池（`assistant-turn-*`）与 Tomcat 工作线程池、以及 messaging 模块的消息线程池
**三个独立**。隔离是双向的：助手慢不会拖垮商城，商城的流量也不会吃光助手的执行线程。

## 三、异步：把「等模型」从 Web 容器线程上挪走

### 改动

```java
@PostMapping("/conversations/{id}/messages")
public Callable<SendMessageResponse> send(@PathVariable String id, Principal principal,
                                         @Valid @RequestBody SendMessageRequest request) {
    String username = principal.getName();
    String message = request.message();
    return () -> service.sendDetailed(id, username, message);   // 在助手线程池里跑
}
```

配套三件事：

1. **助手专用线程池**（`AssistantAsyncConfig`）：core 4 / max 16 / queue 64。
2. **显式把线程池交给 Spring MVC 的异步处理**（`configureAsyncSupport`）。
   不显式指定的后果很隐蔽：Spring Boot 的 `applicationTaskExecutor` 因为有多个线程池
   bean 而**不会被创建**，MVC 会悄悄退化成 `SimpleAsyncTaskExecutor`——**每个请求新建一条线程**，
   并发一高直接雪崩。这类「看起来能跑」的默认降级，正是必须写死配置的原因。
3. **异步超时必须大于 harness 的墙钟预算**（`timeoutMs + 15s`）。
   否则会在循环给出诚实兜底答复之前先被容器掐断，用户什么也拿不到。

用户名在请求线程上就取出并捕获进闭包，异步线程里不再依赖 SecurityContext——
少一次跨线程的上下文传播，就少一处可能静默失效的隐式依赖。

### 关键修复：把事务收窄到「真正碰数据库的那一瞬间」

这是第 1 号致命隐患的解药，也是本次改动里**收益最大**的一处。

```
改前：  |——— 事务（持有一个数据库连接）———|
       查询 → 插消息 → [模型调用 3s] → [模型调用 2s] → 插回复
                          ↑ 全程持有连接，Hikari 12 → 第 13 个并发请求卡死

改后：  |事务| 查询 →  插消息  →[模型调用 3s]→[模型调用 2s]→  |事务| 插回复
         ↑ 毫秒级                                          ↑ 毫秒级
       模型调用期间不持有任何连接 → 同一个 12 连接的池可服务几百个并发轮次
```

实现落在 `AssistantTurnStore`：两段写入各包一个 `TransactionTemplate`，
并显式设置事务超时（10s）。**用代码而不是注解表达边界**，因为这个边界本身就是这个类的全部意义，
写在代码里比藏在注解里更难被后来者误删。

> 语义上的取舍：拆开之后，「插用户消息」和「插助手回复」不再是一个原子操作。
> 但这本来就不是——原实现里模型失败时助手回复仍会写入（错误提示）。
> 现在中途失败时用户消息已经落库，下一轮仍能看到自己说过什么，对用户更友好。

## 四、降级：资源不够时，牺牲并发度而不是牺牲可用性

`AgentLoop` 的并行预算（`max-parallel-tools`，默认 4）是**全局**的，
因为 worker 线程池被所有轮次共享。当预算被别的轮次占满时，本轮的做法是
**就地顺序执行**，而不是排队等许可：

| 策略 | 高并发下的结果 |
|------|----------------|
| 排队等许可（错误做法） | 本轮工具集体堵到 `allOf().get(timeout)` 超时 → **所有用户一起**失败 |
| 就地顺序执行（当前做法） | 只是变慢（单次工具调用本就在毫秒级），每个请求都能完整答完 |

宁可牺牲并发度，也不要牺牲可用性。这就是 `parallelBudgetExhaustionDegradesToSequential`
这条用例锁住的性质。

另外两处防泄漏：许可在任务 `whenComplete` 时释放；若线程池拒绝提交（`AbortPolicy`），
**必须把许可还回去**——否则会被永久泄漏，整个池慢慢饿死。

## 五、测试证据

`mvn verify`：**138/138 通过**（原 124 + 本次新增 14 例）。并发相关的用例集中在两个文件：

**`TurnScopeTest`（6 例，离线确定性）**

| 用例 | 锁住的性质 |
|------|-----------|
| 嵌套还原 | 内层退出回到外层而不是清空 |
| 跨线程传播 | worker 线程上读得到本轮的会话与用户 |
| **池化残留被精确还原** | 人为在 worker 上留下「上一个用户」的上下文，任务执行期间看到的是本轮的，任务退出后还原成残留值而不是 `null` |
| 无轮次时不凭空创建 | 不在轮次内时 `wrap` 原样返回任务 |
| 属性单向隔离 | worker 上的写入不回流到调用线程 |
| `install` 快照 | 装载后读到与快照一致 |

**`AssistantConcurrencyTest`（8 例，Spring 集成 + Mock 模型）**

| 用例 | 锁住的性质 |
|------|-----------|
| **模型调用期间无活动事务** | 直接断言 `TransactionSynchronizationManager.isActualTransactionActive()` 为 `false`——这是「连接池不会被慢请求打空」的机器可验证形式 |
| 同会话串行 | 第一条还在模型里时发第二条返回 `409`，且被拒的请求**不落库** |
| 每用户在途 | 同用户第 3 个会话被 `429`；结束后 `inFlightOf` 归零（无额度泄漏） |
| 全局在途 | 跨用户超额返回 `503`；结束后全局在途归零 |
| **并发下待确认动作归属正确** | 两个用户同时发起支付，各自 `pendingAction.orderId()` 与 `conversationId()` 都是自己的——直接验证轮次上下文没串味 |
| 并行预算耗尽降级 | 许可被排空后，同一轮的两个工具仍**全部 `OK`**（没有一条变 `TIMEOUT`） |
| 消息接口异步 | 返回 `request().asyncStarted()`，`asyncDispatch` 后拿到 200 与回复内容 |
| **异步绑定专用池** | 反射断言 `handlerAdapter` 的 taskExecutor 线程前缀是 `assistant-turn-`——防的是「悄悄退化成 `SimpleAsyncTaskExecutor`（每请求新建线程）」这个安静的坑 |

端到端行为（真实 DeepSeek + 真实登录）沿用既有脚本：
`MALL_URL=... MALL_BROWSER_CHANNEL=msedge node tests/security-eval.cjs`，
异步化对前端透明（`await fetch` 语义不变）。

## 六、配置项

```yaml
mall:
  assistant:
    harness:
      max-parallel-tools: 4         # 全局并行工具预算：所有用户共享，抢不到就顺序执行（不排队等）
    concurrency:
      core-pool-size: 4             # 助手专用线程池核心线程数（与 Tomcat 线程池物理隔离）
      max-pool-size: 16             # 最大线程数，应与 max-in-flight-global 对齐：入池即占一个线程
      queue-capacity: 64            # 队列容量（第二道保险丝；正常情况下在途上限先拦住）
      max-in-flight-global: 16      # 全局同时在途上限，超过 503
      max-in-flight-per-user: 3     # 单用户同时在途上限，超过 429
      serialize-per-conversation: true  # 同一会话串行，并发第二条 409
```

调参口径：**在途上限是口径，线程池是容量，两者必须对齐**。
`max-in-flight-global` 超过 `max-pool-size` 的话，多出来的请求会在队列里干等，把响应时间拖成超时——
等于把「快速失败」偷偷换成了「慢慢失败」，比直接拒绝更糟。

还需要一起看的上游约束：
- `spring.datasource.hikari.maximum-pool-size`（12）：不再被慢请求长期占用后，
  它可以支撑的并发轮次从「约等于池大小」变成「由模型延迟与每分钟请求量决定」；
- 模型提供方的并发配额：本地池再大，上游限流一样会失败。

## 七、真实局限（生产环境该补的）

| 局限 | 说明 | 生产做法 |
|------|------|----------|
| 闸门是单机内存态 | 多实例部署时每个实例各算一份，全局上限形同虚设 | 换 Redis 计数器 / 分布式锁；或前置网关限流 |
| 会话串行用本地锁 | 同上，跨实例不生效 | 分布式锁，或用数据库乐观锁（会话版本号）替代码内锁 |
| 拒绝是「立即失败」而非「排队」 | 用户体验是「稍后重试」；没有排队与公平性保证 | 引入有界队列 + 排队超时提示；或做请求优先级 |
| 没有背压到模型层 | 上游模型限流时只能靠失败重试 | 自适应并发（AIMD）、退避重试、熔断 |
| 异步不返回中间进度 | 用户只能等最终结果 | SSE / 流式输出，或前端轮询运行轨迹接口 |
| 无跨进程取消 | 客户端断开后轮次仍跑到预算耗尽 | 传播取消信号，在循环里检查中断位 |
| 事务收窄后不再「全或无」 | 中途失败会留下用户消息 | 需要时补一次补偿/标记（本项目有意保留，语义更贴近真实对话） |
