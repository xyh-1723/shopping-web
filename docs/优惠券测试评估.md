# 优惠券测试评估：边界、数量与叠加

> 评估日期：2026-10-27。被测对象：`dev.learning.mall.coupon`（V27/V28 表结构与算法）
> 及订单侧的券集成。设计与规则见 [优惠券系统设计方案.md](优惠券系统设计方案.md)，
> 真库验收与对账见 [验证记录.md](验证记录.md) 的「附录：优惠券系统验收」。

本轮新增 **3 个测试类 / 33 条用例**，全部落在「分」上断言，不复用常规场景。
全量回归 **77 个测试类 / 572 条用例，0 失败、0 错误、0 跳过**。

（如实记一笔：首次全量运行时，与本轮无关的 `MockResponseConcurrentHeaderWriteTest` 因 60 秒写线程预算被吃满而超时；
单独跑 **1.18 秒**通过，机器空闲后全量重跑 572/0。这是既有的负载敏感用例，不是券的问题。）

## 0. 结论

| 问题 | 结论 | 决定性证据 |
| ---- | ---- | ---------- |
| 券与促销满减能否叠加？ | **能**，且顺序固定为「先满减、再算券」，券后重新判断包邮 | `CouponStackingAndLifecycleTest#couponStacksOnPromotionDiscount`：118 → 减 10 满减 → 减 10 券 → 98 < 99 → 加运费 8 → 应付 106 |
| 一张订单能否叠多张券？ | **不能**，且不是靠 if 挡的：请求只有一个券实例号，库里唯一键让第二张券**写不进去** | `#databaseRejectsSecondCouponOnSameOrder`：绕过服务层用裸 SQL 写第二张，照样被 `DataIntegrityViolationException` 拒绝 |
| 发行量会不会超发？ | **不会**：条件更新 `WHERE issued_count < total_quantity` | `CouponQuantityTest#concurrentClaimsNeverOverIssue`（10 线程抢 5 张，恰好成功 5）、`#concurrentClaimByDifferentUsersStopsAtStock`（10 人抢 3 张，恰好 3） |
| 每人限领会不会被并发绕过？ | **不会**：模板行 `FOR UPDATE` + `(coupon_id, username, claim_seq)` 唯一键 | `#concurrentClaimBySameUserRespectsPerUserLimit`：8 线程抢限领 2 张，恰好成功 2 次，`claim_seq` 只能是 1、2 |
| 平台预算会不会超支？ | **不会**：条件更新精确到分，退款不会退成负数 | `#concurrentBudgetNeverOverSpends`（12 线程抢 600 分，恰好成功 6 次）、`#budgetBoundaryIsExactToTheCent` |
| 极端金额会不会算出负数？ | **不会**，1000 组随机输入下 10 条不变量无一破坏 | `CouponBoundaryPricingTest#randomCasesKeepEveryInvariant` |
| 边界是否严格到分？ | 是。门槛差 1 分、封顶正好相等、0 基数店、空车、极小折扣取整都有专门用例 | 见 §2 |

一句话：**券可以和促销叠，不能和券叠**；数量的三道闸门（发行量、每人限领、平台预算）都在数据库条件更新上，并发用例证明的是「成功次数恰好等于容量」，而不是「没有超发」——后者靠全拒绝也能做到。

## 2. 边界覆盖矩阵

`CouponBoundaryPricingTest` 逐条对应一个「差一点就错」的位置：

| # | 边界 | 期望 | 实测 | 用例 |
| - | ---- | ---- | ---- | ---- |
| 1 | 门槛正好相等（满 100，货 100.00） | 可减 | 减 5.00 | `minSpendBoundaryIsExact` |
| 2 | 门槛差 1 分（满 100.01） | 拒绝，且提示差额就是 0.01 | `COUPON_MIN_SPEND_NOT_MET`，文案含 `0.01` | 同上 |
| 3 | 商家券的门槛只算本店 | 本店 60 不够 100 → 拒绝；平台券合计 120 → 可减 | 均符合 | `minSpendCountsOnlyEligibleShops` |
| 4 | 促销把基数从 100 降到 60 | 「满 100」不再成立（门槛比券前折后金额） | 拒绝 | `promotionDiscountShrinksTheThresholdBase` |
| 5 | 券额 100 > 商品 60 | 减免被商家封顶压到 21.00，绝不为负 | 21.00；商家收入 35.88、平台 3.12 | `couponLargerThanGoodsNeverGoesNegative` |
| 6 | 券减掉整单商品金额（100% 折扣） | 应付 0，商家/平台收入都是 0，不为负 | 60.00 / 0.00 / 0.00 | `fullDiscountProducesZeroIncomeButNotNegative` |
| 7 | 商家承担正好 = 35% 封顶（35.00） | 不下调 | 35.00 | `merchantCapBoundaryIsInclusive` |
| 8 | 多 1 分（35.01） | 压回 35.00，平台补贴 0 | 符合 | 同上 |
| 9 | 补贴正好 = 佣金 80% | 券后 90 → 佣金 7.20、补贴 5.76、平台 1.44（=佣金 20%） | 符合 | `subsidyCapIsExactlyEightyPercentOfFee` |
| 10 | 平台共担比例 0 | 商家全担，平台收入 = 全额佣金 | 符合 | `zeroPlatformShareMeansMerchantBearsAll` |
| 11 | 某店被满减减到 0 元 | 该店券减 0、收入 0，减免全落另一家 | 符合 | `zeroBaseShopGetsNothing` |
| 12 | 空购物车用券 | 明确拒绝，而不是「减 0 元」 | `COUPON_NOT_APPLICABLE` | `emptyCartCannotUseCoupon` |
| 13 | 极小折扣：0.5% × 0.50 元 = 0.0025 元 | 向下取整 0 分 → 拒绝，绝不四舍五入成 1 分 | 拒绝；同参数在 100 元上正好减 0.50 | `roundingNeverInventsADiscount` |
| 14 | 无券结算遇 0 元店 | 不抛异常，收入 0 而非负 | 符合 | `settleHandlesZeroBaseShop` |
| 15 | 券 + 满减 + 包邮门槛 | 券后 98 < 99 → 运费重新出现 | 应付 106 | `CouponStackingAndLifecycleTest#couponStacksOnPromotionDiscount` |

第 5、7、8 条是本轮最值得留下的三条：它们证明「商家封顶」是按**重新下调后的减免**计算，而不是把券面额硬截断；第 13 条证明算法在整数分上只会向下取整，不会「凑」出优惠。

## 3. 数量处理与并发

### 3.1 三道闸门

| 闸门 | 实现 | 用例 | 结果 |
| ---- | ---- | ---- | ---- |
| 发行量 | `UPDATE coupon SET issued_count = issued_count + 1 WHERE id = ? AND issued_count < total_quantity` | `zeroQuantityMeansSoldOut`、`quantityCanBindBeforePerUserLimit` | 发行 0 张时谁都领不到（`COUPON_SOLD_OUT`，不是「券不存在」）；发行 2 张时同一人只能拿 2 张，第三个用户也是「已领完」 |
| 每人限领 | 模板行 `SELECT ... FOR UPDATE` → `countClaimed` → 唯一键 `(coupon_id, username, claim_seq)` 兜底 | `perUserLimitTwoAllowsExactlyTwo` | 第 3 次 `COUPON_LIMIT_REACHED`，`claim_seq` 恰好 1、2 |
| 平台预算 | `UPDATE coupon SET platform_spent_cents = platform_spent_cents + ? WHERE ... + ? <= platform_budget_cents` | `budgetBoundaryIsExactToTheCent`、`zeroSubsidyNeedsNoBudget` | 300 + 200 正好用满 500；再占 1 分失败且不留痕；退 500 归零；多退 1 分失败且不为负；补贴 0 不写库 |

### 3.2 并发用例（用栅栏，不用 `sleep`）

| 用例 | 线程 | 容量 | 成功次数 | 终态断言 |
| ---- | ---- | ---- | -------- | -------- |
| `concurrentClaimsNeverOverIssue`（仓储层直接抢发行量） | 10 | 5 | 5 | `issued_count = 5` |
| `concurrentClaimByDifferentUsersStopsAtStock`（完整 `claim` 服务） | 10 | 3（每人 1） | 3 | `issued_count = 3`、`user_coupon` 恰好 3 行 |
| `concurrentClaimBySameUserRespectsPerUserLimit`（同一用户） | 8 | 每人 2 | 2 | `claim_seq` 只能是 1、2 |
| `concurrentBudgetNeverOverSpends` | 12 | 600 分 / 每次 100 | 6 | `platform_spent_cents = 600` |

「成功次数恰好等于容量」是有意为之的断言：把所有请求都拒绝同样能保证不超发，但那是另一种故障。用 `CountDownLatch` 让线程同时起跑，是为了逼近条件更新真正面对的时序；线程里抛出的异常不被吞掉——它可能意味着「没抢到」，也可能意味着真出了问题，必须让用例红。并发用例里「被拒绝」的**原因**也要断言（售罄 / 限领），不能把数据库报错算成一次正常失败。

### 3.3 状态与时间窗

- 未开始、已暂停的券：不在可领列表里，直接领也是 `COUPON_UNAVAILABLE`；
- 已领完的券：**仍在列表里**，但 `remainingQuantity = 0`（前端 `app.js#renderCoupons` 按余量置灰按钮），这是后端与前端一致的契约，不是遗漏；
- 锁定中的券过期后再取消：只能变 `EXPIRED`，不能「复活」成 `UNUSED`；
- 读路径会把「已过期但仍是 UNUSED」的券纠正为 `EXPIRED`，避免用户看到一张永远用不了的「有效」券。

## 4. 「是否可叠加」的评估

### 4.1 券 + 促销：可以，且顺序不能反

链路是 `SubOrderSplitter` 先按店拆满减 → `CouponShop` 带上「满减前小计」与「满减分摊」 → `CouponPricing` 用 `goodsAfterPromotion` 作为门槛与减免基数 → `CartPricing.quote(lines, coupon)` 用券后金额重算运费与包邮。

这条顺序有三个直接后果，都有用例守着：

1. 门槛比的是**券前折后金额**，不是原价（真库验收里「满 199 的折扣券在 199 元单品上不可用」，正是这条规则的必然结果）；
2. 券能把包邮资格「打掉」：118 元先减 10 满减后仍 ≥ 99，再减 10 券变 98，运费 8 元随即出现；
3. 券减免不会超过券前折后商品金额（`CartPricing` 硬校验，越界抛异常而不是静默截断）。

### 4.2 券 + 券：不支持，而且是结构性禁止

三层证据：

| 层 | 证据 |
| -- | ---- |
| 接口 | `CreateOrderRequest` 只有单个 `userCouponId`；它还在幂等哈希里，换券重放会被判冲突 |
| 服务 | `CouponService.reserve` 只锁一张券、只占一次预算；`OrderTransactions.splitIntoSubs` 把「一张券的逐店分摊」写进子单六列 |
| 数据库 | `user_coupon` 上的 `uq_user_coupon_locked_order UNIQUE (locked_order_id)`：一笔订单最多挂一张锁定券。用裸 SQL 强写第二张会直接抛 `DataIntegrityViolationException`，第二张仍是 `UNUSED` |

**如果将来要支持叠加**，最小改动清单与风险：

1. 请求：`userCouponId` → 券实例号列表，并校验去重与「最多 N 张」；
2. 表：去掉 `uq_user_coupon_locked_order`，改为 `(locked_order_id, seq)` 唯一；父单的 `coupon_id/coupon_code` 两列改为关联表（或券分摊明细表）；
3. 算法：先定义叠加顺序（平台券先还是商家券先、折扣券与满减券谁先），再定义「合计减免 ≤ 券前折后商品金额」的最终截断；每张券的商家承担与平台补贴仍要逐张满足各自封顶；
4. 预算：多张券的补贴必须在同一事务里一次性预占，任一张失败整体回滚；取消/退款要按券逐张回退；
5. 结算：`order_sub` 六列需要能按券追溯，否则「哪家店为哪张券出了多少钱」对不上账；
6. 幂等：哈希要覆盖整个券集合与顺序。

风险：叠加会把合计减免推到商品金额附近，三角平衡从「一张券的双封顶」变成「一组券的联合封顶」，商家与平台的承担边界更难解释；客服与对账从「一券一行」变成「多券归属」。**当前版本不做多券叠加，是正确的取舍**，不是能力缺口。

### 4.3 券 + 免运费：不是叠加，是同一价格链上的顺序问题

券后金额决定运费，所以「用券反而更贵」这种自相矛盾在结构上不会出现（券后金额仍要加运费，但运费是因为券后跌破包邮线才出现的，页面会同时显示两条说明）。

## 5. 随机性质测试

`randomCasesKeepEveryInvariant` 用固定种子 `20261027L` 跑 1000 组：

- 随机资金参数：佣金 0 / 8% / 20%，商家封顶 0 / 10% / 35% / 100%，补贴上限 0 / 50% / 80% / 100%；
- 随机 1–4 家店，小计 0–500 元，满减 0–小计；券随机为满减或折扣（折扣可带封顶），商家券的店铺号从购物车里真实存在的店中挑；
- 每组断言 10 条不变量：逐店券减 ∈ [0, 商品金额]、券减 = 商家承担 + 平台补贴、商家承担 ≤ 封顶、补贴 ≤ 名义份额、佣金 = 券后金额 × 佣金率、平台收入 ≥ 0、商家收入 ≥ 0、两者之和 = 券后商品金额、Σ 各店 = 券总额、非本店商家券减免为 0。

只允许两种业务拒绝（门槛不足、减不了钱）；门槛不足时还要断言「确实差额」。最后要求成功与拒绝**各至少 100 组**，否则「全拒绝」也能让测试假绿。

固定种子的意义：失败可复现。随机覆盖的意义：逐店向下取整 + 最大余额法 + 二分封顶三者之间的 1 分抖动、封顶越界、负收入，只要存在就会在某个组合上露出来——这些恰恰是常规用例最难手工构造的。

## 6. 覆盖空洞与已知局限

1. **H2 ≠ MySQL**：并发条件更新的语义两边一致，但锁实现不同。真库只做了功能验收与 SQL 对账，没有在 MySQL 上重跑并发用例；要彻底对齐应上 Testcontainers。
2. **不是压测**：并发用例是 8–12 个线程的短时竞争，没有跑吞吐、死锁率、连接池打满等长时指标。
3. **没有多实例验证**：条件更新天然支持多 JVM，但本轮只在单进程内验证。
4. **退款不退券只有代码证据**：`RefundService` 完全不触碰券表，所以「退款后券仍是 `USED`」在结构上成立，但没有专门用例固化这条规则；建议后续补一条（它是反套利设计的一部分，值得被测试锁住）。
5. **过期瞬间与下单的竞态**：`lockForOrder` 用 SQL 条件 `expires_at > now` 兜底，但「刚好在这一毫秒过期」的时序没有专门的用例。
6. **前端无自动化**：售罄券的置灰、券下拉框的金额展示只有手工验收。
