# 订单超时自动关闭 + 弃单挽回

对应代码：`order/`（状态机与扫描）、`proactive/internal/AbandonedOrder*`（召回）。

---

## 一、要解决的不是「少一个定时任务」

用户下单 → 库存被预占 → 用户不付款就走了 → **库存永远扣着**。

在只有 6 件商品的库里，一个人弃单就能让某件商品对所有人显示「卖完了」。
这不是体验问题，是**数据被污染**——而且它每天都在发生。

核对现状后有一个关键发现：

- 库存在**下单时**预占（`OrderTransactions.create` → `catalog.reserve`）；
- 释放库存的逻辑**已经存在**（`cancel()` → `catalog.release`）；
- 缺的从来不是回退能力，而是**一个时间驱动的触发源**。

所以这件事的正确做法不是新写一套回退，而是给已有的关单动作接上第三种触发源
（前两种是「用户主动取消」和「用户已支付」）。

## 二、状态与关闭原因

订单三态：`PENDING` / `PAID` / `CANCELLED`。用户主动取消与系统超时关闭会挤在同一个
`CANCELLED` 里，这不该发生：

| 维度     | 用户主动取消       | 系统超时关闭                     |
| -------- | ------------------ | -------------------------------- |
| 运营指标 | 购买意愿变化       | 支付转化漏斗（是两个完全不同的数） |
| 用户文案 | 「你取消了订单」   | 「订单超时未支付，已关闭，库存已归还」 |
| 后续动作 | **不该打扰**（不想买了） | **弃单挽回的入口**（可以提醒） |
| 责任归属 | 用户行为           | 系统行为（客诉时必须能分清）     |

**落地方式**：`status` 保持三态，新增 `close_reason`（`USER` / `TIMEOUT`）。

### 为什么没有加第四态 `CLOSED`

看起来更干净的做法是加一个 `CLOSED` 状态。但它要求改 V1 里 `status` 的内联
`CHECK (status IN (...))` 约束，而 H2 给这个约束起的是**自动名**——实测是
`CONSTRAINT_51` 这种形式：

```
CONSTRAINT_NAME   CHECK_CLAUSE
CONSTRAINT_51     STATUS IN ('PENDING', 'PAID', 'CANCELLED')
```

把这种名字写进迁移脚本，换个环境或顺序就会失配。**为了一个枚举值的美观度去承担
「迁移在某台机器上失败」的风险，不划算。**

而 `close_reason` 本身也有独立价值：将来还会有「风控关闭」「客服关闭」，
这个列不是为超时一件事而生的。四态语义在**展示与文案层**照样完整。

## 三、`expires_at` 落库，而不是靠配置算

```java
LocalDateTime expiresAt = LocalDateTime.now(clock).plusMinutes(properties.getPaymentTimeoutMinutes());
```

配置会改（15 分钟 → 30 分钟）。如果每次扫描时用「当前时间 − 创建时间」来判定，
那么运营改一次配置，所有存量订单的截止时间会一起跳变——用户明明看到「还剩 2 分钟」，
刷新一下变成「还剩 17 分钟」。

**落库才能保证「下单时承诺给用户的那个时刻」不会中途改变。** 用户看到的倒计时
必须和当初说的一致。

## 四、关单动作只有一份实现

超时关闭 = 用户主动取消的同一个动作，差异只有 `close_reason`：

```java
private boolean close(OrderRow row, String reason) {
    if (orders.markClosed(row.id(), reason, LocalDateTime.now(clock)) != 1) return false;
    for (OrderView.Item item : lines) catalog.release(item.productId(), item.quantity());
    ...
}
```

拆成两份的那天开始，就会出现「主动取消归还了库存、超时关闭忘了归还」这类分叉，
而且它不会立刻暴露。

### 幂等来自影响行数

```sql
UPDATE mall_order SET status='CANCELLED', close_reason=:reason, closed_at=:closedAt
 WHERE id=:id AND status='PENDING'
```

**影响 1 行才表示「这次状态转换是我完成的」**，才去归还库存；0 行说明别人已经处理过
（刚支付 / 已取消 / 已被另一轮扫描关闭），安静跳过、不报错、不重复归还。

### 为什么先改状态、再归还库存

顺序反过来的话，「还了库存但订单没关掉」这个窗口是真实存在的：库存凭空多出来，
而订单还挂着。先做**带条件的状态更新**拿到转换权，再归还——这两步在同一个事务里，
要么都发生，要么都不发生。

## 五、支付与关单的竞态

用户在最后一秒点支付，定时任务同时开跑。两边都先拿订单行锁（`FOR UPDATE`），
再检查状态，所以结果只有两种，**且都必须给出正确反应**：

- **支付赢**：订单变 `PAID`，扫描随后读到 `PAID` 直接跳过；
- **关单赢**：用户收到明确文案「订单超时未支付，已自动关闭，库存已归还，请重新下单」
  （错误码 `ORDER_EXPIRED`）——**绝不能是「未知错误」或笼统的「状态不对」**，
  否则用户只能反复重试。

## 六、扫描：这次为什么不需要游标

上一个目标（关注提醒扫描）刚引入 `last_scanned_at` 游标来防队尾饥饿，这里**不该照抄**：

```sql
SELECT id FROM mall_order
 WHERE status = 'PENDING' AND expires_at IS NOT NULL AND expires_at <= :now
 ORDER BY expires_at, id
 LIMIT :limit
```

被处理掉的订单会**离开结果集**（状态已不是 `PENDING`），队列天然收敛，不存在饥饿。
判断依据是「处理之后这一行还会不会被再次选中」，而不是「上次怎么写的」。

其余两条沿用并加强：

- **单笔一个独立事务**：一笔关不掉（坏数据）不该拖累同批其它订单，否则一个坏行就能让
  一批库存永远回不来；它下一轮还会被选中，不会静默消失。
- **积压可观测**：单轮上限之外的剩余量会被查出来写 WARN。积压持续不为零，
  说明扫描跟不上到期速度（调大上限或调密间隔），而不是假装扫完了。

## 七、弃单挽回（P1）

超时关闭之后，把用户拉回来。这部分在 `proactive` 模块，订单模块只广播事实：

```java
appEvents.publishEvent(new OrderAbandonedEvent(row.id(), row.username(), productIds));
// @TransactionalEventListener(AFTER_COMMIT) → AbandonedOrderService.recover(...)
```

### 只挽回超时，不挽回主动取消

主动取消意味着「我不想买了」，再推荐就是打扰；超时关闭更可能是「忘了 / 犹豫 / 支付卡住了」。
**区分这两种关闭的能力，正是 `close_reason` 存在的意义**——它让同一份关单动作
长出了两种截然不同的后续行为。

### 必须等事务提交

`AFTER_COMMIT` 是硬要求：在关单事务内被唤醒时去查库存，读到的还是**归还之前**的旧值，
于是提醒里写「暂时缺货」，而库里其实已经归还了。用户被召回却买不了，
这条提醒反而把信任又消耗一次。「事件先于数据到达」是事件驱动里最经典的坑，
这里和降价提醒踩的是同一个。

### 幂等靠唯一索引

关单扫描可能重复扫到同一笔订单（上一轮归还库存失败、下一轮重试），
同一个订单不能因此提醒两次：

```sql
ALTER TABLE mall_alert ADD COLUMN source_key VARCHAR(64);
CREATE UNIQUE INDEX uq_alert_source ON mall_alert(username, source_key);
```

用唯一索引而不是「先查有没有、再决定插不插」——查与插之间那一瞬间另一个事务可以插进来，
于是两条提醒同时诞生。`DuplicateKeyException` 在这里不是错误，而是「已经提醒过了」的正常答案。

NULL 不参与唯一性判断（实测 H2 允许多行 NULL），所以既有的降价/到货提醒不受影响。

### 推荐必须带理由，且不能推荐用户刚弃掉的那件

「你可能还想要：樱花便签本（和你近期挑的品类相同）」——没有理由的推荐看起来像广告位，
有理由的推荐看起来像帮忙。同时要把订单里那件商品从推荐结果里过滤掉：
那是揭短，不是帮忙。

## 八、前端：倒计时只是体验

订单卡片显示剩余支付时间，归零后置灰按钮。但**服务端才是唯一权威**：
客户端时钟随手可改，所以倒计时归零后前端不会自己把订单标成「已关闭」，
而是回去问一次服务端。

`mvn -o test` **257 个测试，0 失败**（上一期 234 + 本期 23）。
新增 `OrderExpiryTest`（16 例）与 `OrderAbandonedRecoveryTest`（7 例）。

| 分组             | 例数 | 断言要点                                                                 |
| ---------------- | ---- | ------------------------------------------------------------------------ |
| 下单时的承诺     | 1    | `expires_at` 落库为下单时刻 + 时限；**改配置后存量订单的截止时间不跳变** |
| 到期与否         | 3    | 到期前 1 秒不关；到期即关（状态/原因/关闭时间/库存/事件）；重复扫描只还一次库存 |
| 两种关闭分得开   | 2    | `USER` 与 `TIMEOUT` 可区分；**已支付订单永不被关单命中**（卖出去的货不能被还回来） |
| 关单动作自身     | 2    | 调用方坚持说到期，也不碰已支付订单；已关闭的订单再关一次什么都不做，原因不被覆盖 |
| 竞态             | 2    | 超时后支付得到 `ORDER_EXPIRED` 而非未知错误；20 轮并发下结局永远自洽（状态与库存不会互相矛盾） |
| 原子性           | 1    | 归还库存失败 → 状态不变、库存不动（不是「关了单却没还库存」），故障恢复后下一轮能关掉 |

| 迁移             | 1    | V10 的存量回填语句在本库上真的能跑（`DATEADD` 是 H2 方言，写错就是迁移崩） |
| 用户可感知       | 1    | 超时关闭会通知到用户，通知内容含「超时」                                 |
| 弃单召回         | 7    | 超时关闭会召回且说明东西还在；推荐带理由；**主动取消不召回**；同一订单只召回一次（含 4 线程并发）；开关关闭时不召回但关单照常；召回发生在库存归还之后 |

### 反向验证：写完就绿的测试不证明任何事

两组测试都做了反向验证——把实现临时改回「看起来也行」的写法，确认测试真的会红：

1. 去掉条件更新（`WHERE ... AND status='PENDING'`）与关单前的状态检查 →
   `Failures: 2`（已支付订单被关掉、已关闭订单的原因被覆盖）。

   第一次反向验证时是**全绿的**——因为已支付订单根本不会进入扫描的候选集，
   扫描路径上的测试碰不到这条规则。这暴露了测试盲区，于是补了两个
   **直击关单动作本身**的用例，第二次才变红。
2. 让「用户主动取消」也发出弃单事件 → `Failures: 1`（主动取消被错误召回）。

## 十、边界与没做的事

- **超时判定用的是服务端时间**，前端倒计时仅作体验（客户端时钟可改）。
- **真实支付场景需要支付单与回调幂等**：现在的 `pay()` 是本地无副作用的模拟策略，
  真实系统里「支付回调」与「超时关单」的竞态要靠支付单状态 + 关单前的支付查询来收敛，
  本项目没有支付网关，这条只留在注释里。
- **没做延迟消息**：下单时发一条延迟消息理论上更及时，但消息需要在进程重启后仍有地方存着，
  那是一套持久化与恢复机制；扫描的输入是数据库里的事实，天然容忍重启、漏跑、重复跑，
  代价只是最多晚一个扫描间隔——对「库存别被占死」而言完全可以接受。
- **召回目前只到站内提醒**：外发通道（邮件/短信）需要凭据与退订机制，涉合规，未做。
