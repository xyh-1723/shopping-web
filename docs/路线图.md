## 一、P0：订单超时自动关闭

### 要解决的真问题

不是「少一个定时任务」，而是：

> 用户下单 → 库存被预占 → 用户不付款就走了 → **库存永远扣着**。

在 6 件商品的规模下，一个人弃单就能让某件商品对所有人显示「卖完了」。
这不是体验问题，是**数据被污染**的问题——而它每天都会发生。

现状核对（已读代码确认）：

- 库存在**下单时**预占（`OrderTransactions.create` → `catalog.reserve`）；
- 释放库存的逻辑**已经存在**（`cancel()` → `catalog.release`）；
- 缺的不是回退能力，而是**一个时间驱动的触发源**：现在只有「用户自己点取消」才会释放。

所以这件事的正确做法不是新写一套回退，而是**给已有的关单动作接上第三种触发源**。

### 状态与关闭原因

订单当前三态：`PENDING` / `PAID` / `CANCELLED`。用户主动取消与系统超时关闭会挤在同一个
`CANCELLED` 里，这不该发生——两者的**运营口径、用户文案、后续动作、责任归属**全都不同：

| 维度 | 用户主动取消 | 系统超时关闭 |
| ---- | ---- | ---- |
| 运营指标 | 购买意愿变化 | 支付转化漏斗（是两个完全不同的数） |
| 用户文案 | 「你取消了订单」 | 「订单超时未支付，已自动关闭，库存已归还」 |
| 后续动作 | 不该打扰（人家是不想买了） | **弃单挽回的入口**（可以提醒、可以给券） |
| 责任归属 | 用户行为 | 系统行为（客诉时必须能分清） |

**落地方式（已实测决定）**：`status` 保持三态，新增 `close_reason` 列（`USER` / `TIMEOUT`）。

为什么不用四态：V1 里 `status` 是内联 `CHECK (status IN (...))` 约束，要加 `CLOSED`
就必须先删旧约束。而 H2 给这个约束起的是自动名（实测：`CONSTRAINT_51`），
**把这种名字写进迁移脚本，换个环境或顺序就会失配**。为一个枚举值的美观度去承担
「迁移在某台机器上失败」的风险，不划算。

`close_reason` 本身也有独立价值：将来还会有「风控关闭」「客服关闭」，
这个列不是为超时一件事而生的。

前端把 `(status, close_reason)` 映射成用户可读标签，四态语义在**展示与文案层**照样完整。

### 模型变更（V10）

```sql
ALTER TABLE mall_order ADD COLUMN expires_at TIMESTAMP;
ALTER TABLE mall_order ADD COLUMN close_reason VARCHAR(20);
ALTER TABLE mall_order ADD COLUMN closed_at TIMESTAMP;

-- 存量 PENDING 订单必须回填，否则它们永远关不掉（迁移里最容易漏的一步）
UPDATE mall_order SET expires_at = DATEADD('MINUTE', 15, created_at)
 WHERE status = 'PENDING' AND expires_at IS NULL;

-- 扫描按「状态 + 截止时间」过滤，没有索引就是定时全表扫
CREATE INDEX idx_order_expire ON mall_order(status, expires_at);
```

`expires_at` **落库而不是靠 `created_at + 配置算`**：配置会改（15 分钟 → 30 分钟），
落库才能保证「下单时承诺给用户的截止时间」不会中途跳变——用户看到的倒计时必须和当初说的一致。

### 关单动作只有一份实现

超时关闭 = 用户主动取消的同一个动作，差异**只有 `close_reason`**。
必须收敛成一个 `closeOrder(id, reason)`：拆成两份的那天开始，就会出现
「主动取消释放了库存、超时关闭忘了释放」这类分叉，而且它不会立刻暴露。

状态变更一律带前置条件（这是把状态机落到数据库上的唯一可靠手段）：

```sql
UPDATE mall_order SET status='CANCELLED', close_reason=:reason, closed_at=CURRENT_TIMESTAMP
 WHERE id=:id AND status='PENDING'
```

**影响行数 = 1 才表示「这次是我关掉的」**，才去释放库存；= 0 说明别人已经处理过
（刚支付 / 已取消 / 已超时），直接返回当前状态，**不报错、不重复释放**。幂等就来自这里。

### 支付与超时的竞态

用户在第 14 分 59 秒点支付，定时任务同时开跑。两边都必须先拿订单行锁
（现有 `pay()` 已经是 `FOR UPDATE`），再检查状态。结果只有两种，且都必须给出正确反应：

- **支付赢**：订单变 `PAID`，扫描随后读到 `PAID` 直接跳过；
- **关单赢**：用户收到明确文案「订单已超时关闭，库存已归还，请重新下单」——
  **绝不能是「未知错误」**。竞态测试要专门覆盖这一条。

### 扫描：这次为什么不需要游标

上一个目标（关注提醒扫描）刚引入 `last_scanned_at` 游标来防队尾饥饿，
但**这里不该照抄**：

```sql
SELECT id FROM mall_order
 WHERE status = 'PENDING' AND expires_at <= CURRENT_TIMESTAMP
 LIMIT :n
```

被处理掉的订单会**离开结果集**（状态已不是 `PENDING`），队列天然收敛，不存在饥饿。
判断依据是「处理之后这一行还会不会被再次选中」，而不是「上次怎么写的」。
照抄模式不理解模式，就会带来一份没有必要的复杂度。

### 通知与可观测

- 关单后发 domain event → 复用既有 outbox → notification，用户能看到「订单已超时关闭」；
- 扫描返回本轮关闭数并写日志；异常必须吞掉（定时任务不能让任何请求失败，这是既有约定）。

### 前端

- 订单卡片显示**剩余支付时间**（倒计时），过期后按钮置灰，避免用户点了才知道；
- 倒计时只是体验，**服务端仍是唯一权威**——前端时间不可信（客户端时钟可改）。

### 验收清单

- [x] 超时订单被自动关闭，库存回到商品（释放前后库存数可断言）
- [x] 重复扫描同一订单**只释放一次**资源（幂等）
- [x] 关闭原因可区分：主动取消与超时关闭在数据上分得开
- [x] 支付与关单同时发生时，两种结果都有正确文案，无「未知错误」
- [x] 已支付订单**永远不会**被超时关单命中
- [x] 存量 `PENDING` 订单（`expires_at` 为空）在迁移后被正确回填并最终可关闭
- [x] 释放库存与状态变更在同一事务（中途失败不产生「关了单但没还库存」）

补充：反向验证时发现的盲区——第一条反向验证**没有变红**（已支付订单根本不进候选集，
扫描路径上的测试碰不到关单动作自身的规则），于是补了两个直击关单动作本身的用例，
第二次才红。详见文档「反向验证」一节。

## 三、依赖关系

```
P0 订单超时关闭 ──→ P1 弃单挽回（复用提醒 + 关联推荐，只差一个触发点）
P2 外发通道 ──（若做）──→ 让 P1 的提醒真的能触达用户，而不是只躺在站内信里
```

P0 与 P1 之间是真正的依赖：只做 P0，用户看到的是「订单没了」；
接上 P1，才变成「订单没了，但记得回来看看，东西还在」——后者才是成熟平台的做法。
