# 附录 E：Agent Harness 扩展（2026-10-15）

目标：把内联在 `AssistantService` 里的工具循环，升级成一套具备「有界循环 + 韧性工具层 +

`mvn verify`：**124/124 通过**（新增 `AgentLoopTest` 9 例，旧 115 例全绿无回归）。

| 用例 | 断言的核心性质 |
|------|----------------|
| 多工具一轮 | 两个互不依赖工具都执行、结果按原序回填模型上下文 |

| 停滞检测 | 第一轮 OK、第二轮 DUPLICATE（未重复执行）、第三轮主动停止，写 `AGENT_STALLED` |
| 预算耗尽 | 只调用一次模型即停止，记 `MAX_STEPS`，回诚实兜底文案 |
| 轨迹开关 | 关闭后不落库，回答照常 |
| 接口隔离 | 轨迹接口顾客 403 / 店员 200 |

## 本轮发现并规避的一个静默故障

并行化工具调用时差点引入一个不报错的 bug：`PendingActionService` 用 `ThreadLocal` 传递
「当前会话 id」（有意设计——模型自报的会话 id 可被注入篡改）。若把 `requestPayment` 放到
worker 线程执行，它不会抛异常，只是 `CURRENT_TURN.get()` 拿到 null，于是**支付确认卡片静默消失**，
而模型照样回复「已发起支付」。

处置：新增 `@Effectful` 注解标记效果型工具类，`ToolRegistry` 据此推导每轮工具包的效果型名单，
`AgentLoop` 把这类调用留在调用线程顺序执行，其余只读工具并行。并补了针对性回归测试
（`effectfulToolKeepsTurnContextWhenMixedWithReadTools`）——这类静默失败没有测试兜不住。

## 观测层的两条实现约束

1. **轨迹写入失败不得影响回答**：`RunTraceRepository.save` 整体 try/catch，失败只降级为 warn 日志。
   把观测写成会抛异常的强依赖，等于埋一个「监控挂了业务也挂了」的故障。
2. **非正常结束必须留痕**：`stopReason != DONE` 时写审计（`AGENT_MAX_STEPS` / `AGENT_TIMEOUT` /
   `AGENT_STALLED`）。预算类问题如果只在日志里，永远不会有人去调参数。

# 附录 F：多用户并发隔离与异步执行（2026-10-15）

目标：让助手在「多用户同时提问」时依然正确、可控。设计与取舍见 `docs/并发隔离与异步设计.md`。

## 排查结论：两个致命隐患

1. **事务跨越模型调用**。`AssistantService.sendDetailed` 挂着 `@Transactional`，方法体内有 1–6 次
   大模型调用——一整轮对话从头到尾独占一个数据库连接（十几秒）。Hikari 池只有 12，
   第 13 个并发提问就会卡在等连接上；而且商城的下单/查商品/登录共用这个池，
   **助手慢会拖死整个站点**。这是本次发现的最严重问题。
2. **同步阻塞 Web 容器线程**。Controller 同步返回，模型调用期间 Tomcat 工作线程被占住干等；
   默认 200 个线程，几十个「等模型」的助手请求就能吃干净。

另外四个次级隐患：轮次上下文是裸 ThreadLocal（工具 worker 池化复用 → 跨用户串味，
当前靠 `@Effectful` 侥幸规避，是约定不是机制）、同一会话无串行（历史顺序错乱）、
只有频次限制没有在途限制、并行工具池全局共享且只有 4 线程（高并发下集体超时）。

## 本轮的两个设计教训

1. **「清空」和「还原」不是一回事**。池化线程上的上下文，退出时必须还原成进入前的值：
   清空会把不属于你的状态弄丢，同样是破坏性副作用。`workerContextIsRestoredNotJustCleared`
   专门锁住这条——它人为在 worker 线程上留下一份「上一个用户的残留」再验证还原行为。
2. **单向传播是特性不是缺陷**。`TurnScope.wrap` 传下去的是快照副本，worker 上的写入不回流。
   这既保证了并行只读工具无法改写轮次状态，也直接推导出「需要产生产物的工具必须留在调用线程」
   ——这正是 `@Effectful` 当下的技术理由（原来是「怕 ThreadLocal 读不到」）。

## 已知局限

闸门与锁都是单机内存态（多实例部署需换 Redis / 分布式锁或前置网关限流）；
拒绝是立即失败而非排队（无公平性保证）；无背压到模型层；异步不返回中间进度（未做 SSE，
**已于同日的附录 H 补齐**）；无跨进程取消。逐条对应做法见设计文档第七节。

### 两个关键决策（都有实测依据）

| 决策 | 依据 |
| ---- | ---- |
| `status` 保持三态、新增 `close_reason`（`USER`/`TIMEOUT`） | 加第四态要先删 V1 的内联 `CHECK`，而 H2 给它起的是自动名（实测 `CONSTRAINT_51`）。把这种名字写进迁移，换个环境就失配 |

### 本轮发现并修复的问题

| 问题 | 性质 | 处理 |
| ---- | ---- | ---- |
| 关联推荐的同类目文案为「和你**关注**的品类相同」 | 文案失真 | 种子是购物袋与历史订单，与「关注商品」无关；改成「和你**近期挑的**品类相同」。本期起「关注」已是专有功能名，同词不同义会让人以为推荐读的是关注列表 |

（4 条历史 + 1 条新增 = 5）。

### 反向验证：四条里有一条验的是测试自己

| # | 注入的 bug | 预期变红 | 实测 |
| - | ---------- | -------- | ---- |
| 1 | `OrderTransactions#create` 改回裸求和 | 一致性断言红 | ✅ 6 例中 4 例红：`expected: 86.00 but was: 78.00`、`expected: 105.00 but was: 107.00`（两个方向都被抓到） |
| 2 | `pay_amount` 列写成 `subtotal` | 不变量断言红 | ✅ 6 例**全红**，两条 SQL 不变量断言被点名。与 ① 互补：① 抓「绕过定价器」，② 抓「列之间写串」 |
| 3 | `requestOrderCreate` 直接落单（跳过闸门） | 零副作用断言红 | ✅ 3 例红：`unconfirmedCreatesNoOrder`、`loopProducesConfirmationCardWithoutSideEffects`、`foreignUserCannotConfirm` |
| 4 | 原子迁移去掉 `WHERE status='PENDING'` | 重复确认断言红 | ❌ **第一次全绿**——见下 |

**第 4 条为什么没红**：`resolve()` 在调 `execute()` **之前**已经预检过状态，
串行重复确认根本走不到原子迁移那一步。所以那条断言（原名为
「重复确认只落一笔订单」）实际只证明了**预检有效**，没证明**一次性迁移有效**。
而一次性迁移真正防的是**并发**：两个请求同时通过预检、同时去抢同一行，
才轮到它决定「谁把状态改掉了，谁才有权执行」。

**修正**：把原用例改名为 `secondConfirmIsRejectedByPrecheck`（注释里写明它覆盖的是哪一层），
另加 `concurrentConfirmProducesExactlyOneOrder`：2 线程 + `CyclicBarrier` 起跑，跑 12 轮堆高交错概率，
断言「恰好一个请求拿到状态转换权」「落败方必须是 `ALREADY_RESOLVED` 这类业务异常，不能是 500」
「订单只落一笔」「库存只扣一次」。
重做反向验证 → 第 0 轮就红：`expected: 1L but was: 2L`。

这与上一期（附录 J）「反向验证第一次是全绿的」是同一类教训，值得单独记一句：
**写完就绿的测试不证明任何事；但「故意注回 bug 仍然绿」也不一定证明测试没用——
它可能只是证明你测的是另一层。**

  但没有乐观锁版本号。同账号多标签页同时下单，以数据库判定的先后为准。

  按计划应在商品扩到几百件时实施，本轮未做。

## 附录 L：P1-6 服务端清袋（2026-10-16 夜）

### 缺陷：同一个业务动作，三条路径三种结果

| 路径 | 修复前 | 问题 |
| --- | --- | --- |
| 助手确认下单 | 服务端清袋（与落单同事务） | 正确 |
| 页面下单 | **前端**清，`app.js` 里 `DELETE /api/cart` 且失败被 `.catch(() => {})` 静默吞掉 | 袋子可能留着，用户毫不知情 |
| API 直调下单 | 没人清 | 袋子一定留着 |

判断标准不是「有没有代码在清」，而是**用户能不能靠行为预测结果**——不能，所以定性为一致性缺陷，
不是「缺个功能」。

### 方案：同步应用事件，方向 cart → order

`order` 模块不允许依赖 `cart`（当初正是为此把定价器独立成 `pricing` 包），
所以不能让 `OrderTransactions` 直接调 `cart.clear`。改为：

- `order/api/OrderPlacedEvent` —— 在**下单事务之内**发布（不是 AFTER_COMMIT，否则有可见窗口）；
- `cart/internal/CartClearingOnOrderPlaced` —— `@EventListener` 清袋。

依赖方向变成 cart → order，规则保持；两条路径自动统一，不需要各自写一遍。

### 踩到的坑：给 `@EventListener` 加 `@Transactional` 会让既有测试变红

第一版在监听器上加了 `@Transactional`，结果 `OrderExpiryTest#expiredOrderIsClosedAndStockReturns` 变红
（断言最新 outbox 事件是 `ORDER_CLOSED_TIMEOUT`，实际拿到 `ORDER_CREATED`）。
对照实验确认：移除该注解后 16/16 全绿。

原因是给监听器叠事务注解会注册额外的事务同步器，干扰订单发件箱 `AFTER_COMMIT` 的时序。
**不加也照样在同一事务里**：同步发布的事件与发布方同线程同事务，
事务边界由发布方决定，不由监听方决定。

### 验证

- 新增 `ServerSideCartClearingTest` 3 例：页面路径服务端清袋 / 两条路径一致 / **下单失败时袋子必须保留**（不能误清）。
- 反向验证：移除事件发布 → 2 例变红（`pageCheckoutClearsCartOnServerSide`、`bothPathsBehaveTheSame`）。
  第 3 例未红是预期的——它守的是反方向。
- 全量：`mvn -o test` **276 全绿**（上期 272 + 新增 3 + 1 条默认关闭的基准）。

### 顺带清理

`CartCheckout` 端口失去唯一消费者后删除（与 V13 去掉 `request_hash` 死列同理）；
前端 `app.js` 的清袋行移除——服务端已保证，前端那行既是冗余请求，又是「静默吞错」的源头。

## 附录 M：T12 履约闭环——约束异常不许冒泡成 500（2026-10-17）

### 报来的缺陷，以及它在 HEAD 上为什么复现不出来

| 项 | 内容 |
| --- | --- |
| 报告现象 | `POST /api/orders/{id}/ship` 返回 500，堆栈 `DataIntegrityViolationException: Check constraint violation: "CK_ORDER_FULFILLMENT_NEEDS_PAID"` |
| 客户端后果 | 500 被归类成「服务端抖动 / 可忽略异常」，线上等于静默 |
| HEAD 上复现 | **复现不出来** |

判定链：`markShipped` 的 WHERE 里带着 `status='PAID' AND fulfillment_status='NONE'`，
未支付订单在这一步就落空（影响 0 行）→ `INVALID_STATE` / 409，**没有机会走到约束那一步**。
报告的堆栈产生于 V15（履约状态机）落地之前。

### 落地：只翻译，不预判

判定权仍在数据库，只在异常**逃逸到服务边界之后**做一件事：

- 命中本项目自己起的履约约束名（`ck_order_fulfillment_needs_paid` / `_fields` / `_status`）→ 409 + `FULFILLMENT_*` 业务码；
- 命中不了 → 原样抛出，继续 500。把未知的数据层错误也翻译成「业务冲突」等于把真 bug 藏起来。

刻意**没有**把数据库不变式复制成 Java 前置校验：单条 UPDATE 仍是唯一的裁决者，
谁绕过 Service 直接改库，规则依旧在。五处写调用（发货 / 收货 / 完成 / 自动收货两步）全部包在 `guarded` 里。

### 诚实边界：这三条约束名都构造不可达（已写进 Javadoc）

`FulfillmentService` 类注释新增「诚实边界」一节，明写三件事：

1. **构造不可达**：每条 UPDATE 的 WHERE 已经保证了对应的 CHECK（`status='PAID'` 就是
   `ck_order_fulfillment_needs_paid` 的充分条件），所以这三条约束今天没有机会拒绝任何一次 UPDATE；
2. 守的不是「一条现在会发生的路径」，而是**失败形态的选择（failure-mode policy）**：
   以后谁把 WHERE 挪走、漏写一个时刻、或加了新迁移却忘了同步状态机，数据库照样把他打回，
   区别只在于对外是「409 + `FULFILLMENT_*` 语义」还是「500 + 一条被调用方静默的堆栈」；
3. 不允许反过来把它写成「解释了某条真实可达路径」——那是伪造事实。

### 真实 H2 报错原文（探针实测，不是照文档抄的）

```
Check constraint violation: "CK_ORDER_FULFILLMENT_NEEDS_PAID: "
Check constraint violation: "CK_ORDER_FULFILLMENT_FIELDS: "
Check constraint violation: "CK_ORDER_FULFILLMENT_STATUS: "
```

三条各自只踩一条约束（已实测确认），翻译层按「约束名 + 冒号」匹配，与这个形态对齐。

### 已知局限（不藏）

1. `realH2ConstraintNamesAreToldApart` 的三条 UPDATE 是**测试自己拼的**，不是业务代码会发出的语句。

   后者按上一节是构造不可达的。
2. 三条用 spy 注入的用例，证明的是「写调用抛约束异常 → 409」这条链路，而不是某段具体 SQL 文本。
