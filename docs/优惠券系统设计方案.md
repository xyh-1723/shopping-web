# 优惠券系统设计方案（需求 + 算法 + 计划）

## 1. 目标与范围

在不破坏现有「唯一金额入口」和「子订单金额守恒」两条硬约束的前提下，加入一套可领、可用、可对账的优惠券系统：

- 用户：浏览可领券、领券、下单时选券、看到优惠明细。
- 商家：可创建本店券；承担自己那部分优惠，但单笔承担有上限。
- 平台：可创建平台券；按比例与商家共担，且补贴额永远不超过本单平台佣金。
- 财务：每笔子订单留存 `优惠券减免 / 商家承担 / 平台补贴 / 平台佣金 / 商家收入 / 平台收入`，可逐单对账。

**不做**：叠加多张券、券转让、券膨胀、跨平台结算、真实资金清分、优惠券推荐算法。当前版本一张订单最多用一张券。

## 2. 三角平衡：先把「谁出钱」说清楚

很多优惠券系统出问题，不是折扣算错，而是**折扣没有主人**：用户看到减 20，订单只记减 10，另外 10 从商家货款里悄悄消失，或者反过来平台默默兜底。所以本设计先定义资金流，再定义折扣规则。

### 2.1 记法

单张子订单（一家店）内，所有金额均为整数分：

| 符号 | 含义 |
| --- | --- |
| `S` | 该店商品小计 |
| `P` | 该店分摊到的满减（平台既有促销，商家承担） |
| `C` | 该店分摊到的优惠券减免 |
| `F` | 该店分摊到的运费（归商家） |
| `fee` | 平台佣金 |
| `sub` | 平台补贴（平台承担的那部分 `C`） |
| `mc` | 商家承担（`C - sub`） |
| `pay` | 用户为该子订单实付 `S - P - C + F` |

### 2.2 结算公式

```
佣金基数      B      = max(0, S - P - C)
平台佣金      fee    = floor(B × 佣金率)
平台补贴名义  subNom = floor(C × 平台共担比例)
补贴上限      cap    = floor(fee × 补贴上限比例)      // 默认 80%
平台补贴      sub    = min(subNom, cap)
商家承担      mc     = C - sub
商家收入      mi     = pay + sub - fee
平台收入      pi     = fee - sub
```

恒等式：

```
mi + pi = pay
C = mc + sub
pi >= 0                       （因为 sub <= cap <= fee）
```

### 2.3 三条平衡线

1. **用户侧**：券面额真实可用，门槛按「满减后的商品金额」判断，运费不参与抵扣；优惠后若低于包邮门槛，运费重新计算，不制造「用券反而更贵」的错觉。
2. **商家侧**：商家承担封顶，默认 `mc <= (S - P) × 35%`。超过时自动把该店优惠券减免下调到封顶以内，宁可少减，不让商家倒贴。
3. **平台侧**：平台补贴封顶为佣金的 80%，所以平台每笔用券订单至少留下 20% 佣金；平台不会为了发券把佣金全赔进去。

### 2.4 为什么平台还要对无券订单收佣金

若只在用券订单记佣金，平台收入会随发券量波动，且无法回答「这笔券到底让平台赚了还是赔了」。本版对所有子订单都记 `fee / mi / pi`，用券订单只是多出 `sub / mc` 两列。这样券的增量成本可以直接对比：

```
券带来的平台净收入 = pi(用券单) - fee(若不用券)
```

默认参数：佣金率 8%，商家承担上限 35%，平台补贴上限为佣金的 80%。

## 3. 券模型

### 3.1 券模板（coupon）

| 字段 | 说明 |
| --- | --- |
| `owner_type` | `PLATFORM` / `MERCHANT` |
| `merchant_id` | 商家券必填；平台券为空 |
| `discount_type` | `AMOUNT`（满减） / `PERCENT`（折扣） |
| `discount_value` | 满减为元；折扣为百分数（如 `10.00` 表示 9 折） |
| `max_discount` | 折扣券的封顶金额，可空 |
| `min_spend` | 门槛，按券适用商品的满减后金额判断 |
| `platform_share_bps` | 平台共担比例；商家券固定 0，平台券默认 6000 |
| `total_quantity` / `issued_count` | 发行量与已领量 |
| `per_user_limit` | 每人限领 |
| `platform_budget_cents` / `platform_spent_cents` | 平台补贴总预算与已占用 |

### 3.2 用户券实例（user_coupon）

状态机：

```
UNUSED --下单锁定--> LOCKED --支付成功--> USED
   ^                    |
   |                    +--取消/超时--> UNUSED（未过期）或 EXPIRED（已过期）
   |
   +--到期--> EXPIRED
```

- 锁定与订单号绑定（`locked_order_id`），同一张券不可能同时被两笔订单占用。
- 支付成功才核销；取消/超时释放，并把已占用的平台补贴预算退回。
- 退款不退还券（券已核销），这是本版明确取舍：避免「用券下单→退款→券又回来」被反复套利。退款金额仍以用户实付为上限（现有退款逻辑不变）。

## 4. 优惠算法

### 4.1 适用范围

- 商家券：只作用于该 `merchant_id` 的商品，门槛也只看该店折后金额。
- 平台券：作用于全车，门槛看全车折后商品金额。

### 4.2 门槛

```
适用商品折后金额 = Σ(该店 S - P)      （不含运费）
若 < min_spend → 拒绝，错误码 COUPON_MIN_SPEND_NOT_MET
```

### 4.3 折扣计算

- 满减券：目标减免 `min(面额, 适用商品折后金额)`。
- 折扣券：先按每店 `floor((S - P) × 折扣百分比)` 计算；若总额超过 `max_discount`，把 `max_discount` 按各店折后金额占比重新分配。

### 4.4 跨店分摊

平台券可能覆盖多家店。总减免按各店折后金额占比分摊，采用**最大余额法**：

1. 每店 `floor(总额 × 本店基数 / 总基数)`；
2. 取整剩下的分，按余数从大到小每店补 1 分；
3. 余数相同按店序（子订单序号）升序，保证同一输入得到同一结果。

这保证了 `Σ 各店 C = 券总减免`，与现有 `SubOrderSplitter` 的金额守恒思路一致。

### 4.5 商家承担封顶

对每个店：

```
cap = floor((S - P) × merchantMaxBearBps / 10000)
若 mc(C) > cap，则二分查找最大的 C' <= C 使 mc(C') <= cap
```

`mc(C) = C - min(floor(C×share), floor(fee(S-P-C)×capRate))` 在整数分上单调不减，二分可用。

### 4.6 平台预算

下单锁定券时，在同一事务内做条件更新：

```sql
UPDATE coupon
   SET platform_spent_cents = platform_spent_cents + :sub
 WHERE id = :id
   AND status = 'ACTIVE'
   AND platform_spent_cents + :sub <= platform_budget_cents
```

影响 0 行 = 预算不足，抛 `COUPON_BUDGET_EXHAUSTED`，整个下单事务回滚（券不会被锁、库存不会动）。

## 5. 数据库设计（V27）

### 5.1 新表

- `coupon`：券模板。命名 CHECK 约束覆盖：归属与店铺、券类型、折扣值、数量、预算、时间窗、状态。
- `user_coupon`：用户券实例。命名 CHECK 约束覆盖：状态与锁定/核销字段的对应关系；唯一键 `(coupon_id, username, claim_seq)` 保证并发领券不会超发。

### 5.2 订单表扩展

`mall_order` 新增：

```
coupon_discount DECIMAL(12,2) NOT NULL DEFAULT 0
coupon_id       VARCHAR(36)
coupon_code     VARCHAR(32)
```

约束：`coupon_discount <= discount`，且「有减免必须有券号、无减免必须无券号」。

`order_sub` 新增结算六列：

```
coupon_discount  merchant_discount  platform_subsidy
platform_fee     merchant_income    platform_income
```

约束：

```
coupon_discount = merchant_discount + platform_subsidy
merchant_income = pay_amount + platform_subsidy - platform_fee
platform_income = platform_fee - platform_subsidy
merchant_income >= 0, platform_income >= 0
```

存量订单回填 `merchant_income = pay_amount`，其余为 0，重新满足约束。

## 6. 接口

| 方法 | 路径 | 角色 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/coupons` | 登录 | 可领券列表（含剩余量、我是否已领） |
| GET | `/api/coupons/mine` | 登录 | 我的券（含状态） |
| POST | `/api/coupons/{id}/claim` | 登录 | 领券 |
| POST | `/api/coupons` | STAFF / MERCHANT | 创建券模板；商家只能建本店券 |
| POST | `/api/checkout/preview` | 登录 | 用券后的结算预览（不锁券、不写库） |
| POST | `/api/orders` | 登录 | 请求体新增可选 `userCouponId` |

错误码：`COUPON_NOT_FOUND` / `COUPON_UNAVAILABLE` / `COUPON_MIN_SPEND_NOT_MET` / `COUPON_LIMIT_REACHED` / `COUPON_SOLD_OUT` / `COUPON_BUDGET_EXHAUSTED` / `COUPON_NOT_APPLICABLE`。

## 7. 订单链路集成

```
购物车行
  → Pricer.quote(lines)                      满减 + 运费（券前）
  → 按店分组 + 满减分摊                        promotion shares
  → CouponRedemptions.reserve(...)            算券、锁券、占预算（同事务）
  → Pricer.quote(lines, couponDiscount)       重新计算包邮门槛与运费
  → SubOrderSplitter.split(...)               满减/运费按店拆分
  → 叠加各店券减免与结算六列
  → 落 mall_order / order_item / order_sub / outbox
```

关键点：

- **价格快照仍按券前应付比较**：快照只保护「商品价格 / 满减没变」，券折扣由服务端实时算。用户改券后重新下单即可。
- **幂等哈希包含 `userCouponId`**：同一幂等键换券会被判为 `IDEMPOTENCY_CONFLICT`，不会出现「换券重放拿到旧订单」。
- **券锁定在下单事务内**：库存不足、价格变化等任何失败都会连带回滚券状态与预算。
- **支付成功才核销**；取消/超时释放并退预算。
- **退款沿用现有规则**：退款金额不超过子订单实付，券不退回。

| 6 | 订单集成：`OrderTransactions.create` 接券、`splitIntoSubs` 写六列、支付核销、关单释放 | `CouponIntegrationTest` 后 6 例 + `PriceChangeGuardTest` 参数更新 |

两条纪律：

- **先迁移后代码**：表约束是最后一道防线，代码写错时应当被数据库拦下，而不是等对账时才发现。
- **参数不写死**：佣金率、商家封顶、平台补贴上限全在 `mall.coupon.*`，改运营策略不动代码。

### 9.1 自动化测试

   - 结论与覆盖矩阵见 [优惠券测试评估.md](优惠券测试评估.md)。

### 9.2 真库验收（MySQL 3306）

1. 启动应用（MySQL `mall` 库），确认 V27/V28 迁移成功。
2. 登录 `student`，领取平台券与商家券。
3. 调预览接口，核对券后应付 = 小计 − 满减 − 券减免 + 运费。
4. 下单并支付，查 `order_sub` 六列，验证：
   - `Σ coupon_discount = mall_order.coupon_discount`
   - `Σ pay_amount = mall_order.pay_amount`
   - `platform_income = platform_fee - platform_subsidy >= 0`
   - `merchant_income = pay_amount + platform_subsidy - platform_fee >= 0`
5. 再下一单后取消，验证券回到 `UNUSED` 且 `platform_spent_cents` 退回。
6. 用 `admin` / `merchant` 各创建一张券，验证角色与归属约束。

## 10. 风险与后续

- 当前平台佣金只记账，不做真实清分；接入支付通道后需按 `order_sub` 六列出结算单。
- 券预算的并发安全依赖条件 UPDATE；多实例下不会超发，但预算即将耗尽时会出现少量请求失败，这是有意的「宁可拒绝、不可超支」。
- 退款不退券是反套利取舍；若未来要退券，需要新增「券回退」状态与幂等键，不能在退款事务里直接改 `USED → UNUSED`。
- 后续可扩展：券叠加规则、品类券、新客券、券效果归因报表。
