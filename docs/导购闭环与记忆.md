# 导购闭环与记忆

本文记录助手从「会查会答」走向「会导购」的这一期改造。

上一期解决的是「可靠性」：有界循环、并发隔离、安全闸门。这一期解决的是「像不像专业导购」。
差别不在模型，而在 agent 手里有什么：**能不能把东西放进用户的购物袋、能不能记住用户是谁、
需求不清楚时会不会先问一句。** 这三件事决定了用户是用一次还是用一年。

## 一、能力对照

| 能力 | 专业导购的做法 | 本期之前 | 本期之后 |
| ---- | -------------- | -------- | -------- |
| 购物袋 | 替用户加购、改量、算钱 | ❌ 只在浏览器 localStorage 里 | ✅ 服务端购物袋，助手与页面共用 |
| 金额 | 结算金额与页面完全一致 | ❌ 助手凭上下文估算 | ✅ 单一计算入口，满减/运费/凑单同一处算 |
| 记忆 | 下次还记得你的预算和忌讳 | ❌ 每轮从零开始 | ✅ 语义记忆（跨会话）+ 工作记忆（会话摘要） |
| 澄清 | 信息不足时先问关键问题 | ❌ 直接给三件商品 | ✅ 结构化追问 + 前端可点选项 |
| 对比 | 一次把参数摆在一起比 | ⚠️ 分多次搜索后凭上下文拼 | ✅ compareProducts 一次取全 |
| 透明度 | 用户能看到并清除记忆 | — | ✅ 「我的偏好」面板，逐条可删 |

## 二、服务端购物袋：一个被低估的前置条件

原来购物袋存在 `localStorage`。这对纯前端商城没问题，但助手一插手就立刻断裂：
助手在服务端加购、用户在浏览器里看不见，两份状态必然分裂。

因此本期把购物袋搬到服务端（`mall_cart_item`），并顺手解决了一个更隐蔽的问题——
**金额只有一处算法**：

```
购物袋页面 ─┐
下单结算   ─┼─→ Pricer.quote()  ← 满减档位、包邮门槛、运费
助手对话   ─┘
```

规则放在 `mall.shopping` 配置里，算法实现在 `CartPricing` 里。于是「对话里说减 10、结算只减 5」
这类事故在结构上不可能发生——不是靠提示词叮嘱模型别算错，而是让模型根本没有自己算的机会：
工具返回的是服务端算好的数字，提示词明确要求「一律引用，不要心算」。

> **更正（对标淘宝专项）**：这张图在这一期写的时候，其实只画对了两根线。
> 「下单结算」那一根是断的——`OrderTransactions` 一直自己裸求和，没走定价器，
> 于是同一袋东西「袋子显示 ¥86、下单只收 ¥78」「袋子显示 ¥174、下单却收 ¥199」两个方向都会错。
> 也就是说，文档里的承诺比当时的代码早了一步。
>
> 现在补齐了：`Pricer` 接口与 `CartPricing` 实现从 `cart.internal` 独立成
> `dev.learning.mall.pricing` 包——**不是**为了分层好看，而是依赖方向不允许反着来：
> order 要复用定价器，若定价器留在 cart 包里，order 就得依赖 cart。
> 补齐之后，图上的三根线第一次同时成立，并且由
> `CheckoutAmountConsistencyTest`（两条链路差值必须为 0）钉死。

**为什么加购不需要二次确认，支付却需要？** 判据不是「是不是写操作」，而是「写错了代价多大、能不能撤销」：

- 加购：不动钱、用户立刻看得见、一键可撤销 → 直写，但保留库存校验与数量上限；
- 支付：不可逆、发生在后台、用户看不见 → 必须 human-in-the-loop。

把什么都塞进确认流程，只会让确认卡片变成噪音；用户对噪音麻木之后，真正的支付确认也会被随手点掉。

## 三、记忆：一条需要认真设防的通道

记忆是大模型应用里最容易被做糙的部分，难点不在读写，而在**边界**。记忆是一条
「用户输入 → 数据库 → 系统提示」的持久通道：今天写进去一句话，会在之后每一次对话里
被读进最高权限区域。所以：

1. **键白名单**（`MemoryKeys`）：只能存 11 种购物偏好（预算、品类、忌讳、送给谁…）。
   模型写不进任意结构，也就无法把「你的新规则是……」写成一条记忆。
2. **写入过守卫**：值在入库前按不可信输入处理，命中规则直接拒写并记审计。
3. **读出再过守卫**（`AssistantMemoryService`）：数据可能被旧版本或人工途径写脏，
   守卫规则也会升级，所以读取时再查一次；命中即跳过，不进提示词。
4. **有上限、会过期**：单人 8 条、90 天。陈旧偏好比没有偏好更有害——
   两年前说过一次喜欢红色，不该影响今天的推荐。
5. **用户可见可删**：助手页「我的偏好」面板逐条展示、可单删、可全清。
   不可见的记忆会让人不安，而信任是复购的前提。

记忆分两层，各管一件事：

| 层 | 载体 | 作用范围 | 解决什么 |
| -- | ---- | -------- | -------- |
| 语义记忆 | `assistant_user_memory` | 跨会话 | 用户是谁、偏好什么 |
| 工作记忆 | `assistant_conversation_summary` | 本会话 | 窗口之外聊过什么 |

工作记忆是**增量滚动摘要**：消息超出上下文窗口后，把窗口外的部分压成一段摘要补回上下文。
不每轮都摘（省一次模型调用），只在新增消息攒够一批时刷新。摘要本身也是模型产出、内容源自用户，
所以落库前同样过输入守卫——这跟知识库投毒是同一类问题，只是通道从文档换成了对话历史。

上下文因此变成三层，互不替代：

```
系统提示 + （长期记忆：用户画像） + （会话摘要：早期内容） + 最近 N 条原文 + 当前消息
```

## 四、像导购一样互动

- **先问再推**：需求太模糊时，`requestClarification` 抛出一个结构化问题，
  选项由前端渲染成可点按钮。用户不想打字，只想点一下——这是转化率最高的一步。
- **一次比完**：`compareProducts` 一次拿全 2-4 件商品的真实参数，而不是分多轮搜索后在上下文里拼。
- **会算凑单**：`viewCart` 返回小计、满减、运费和「还差多少包邮 / 再买多少能减」，
  这些提示语也由服务端算好，助手直接转述。
- **能替你把这一单买了**（对标淘宝专项新增）：`createOrder` / `cancelOrder` 两个工具，
  让「帮我买下」这句话第一次真的走进成交环节，而不停在加购。详见下节。

## 五、成交闭环：助手能下单，但下不了手

这一节是「对标淘宝」专项补的那一跳。在此之前，助手能把商品加进购物袋、能发起支付确认，
却**不能下单**——创建订单的唯一入口是页面接口，而支付工具只能对付已存在的订单。
于是导购闭环缺了最后一环：用户说「帮我买下」，助手只能让他自己去点。

补齐的方式不是「给助手再写一套下单」，而是把页面的那一份实现通过端口暴露出来
（`OrderCheckout`），助手的确认回调和页面的 `POST /api/orders` 走的是同一段代码。
**安全关键逻辑只有一份实现**，这是这个项目反复出现的决策。

**为什么下单必须 human-in-the-loop，加购不用**：判据是「写错了代价多大、能不能撤销」。
下单占用库存、对店员可见，不可撤销程度高于加购，所以只能发起、不能执行。
这里没有新建第二张待确认表——`assistant_pending_action` 增加 `kind` 列，
`ORDER_PAYMENT` / `ORDER_CREATE` / `ORDER_CANCEL` 三类共用同一道闸门：
归属硬校验、一次性原子迁移、TTL、审计。复制出第二份，就是这些规则分叉的开始。

**确认之前零副作用**是这里唯一的核心不变量，并且是用**行数**证明的：
`unconfirmedCreatesNoOrder` 断言的是 `mall_order` 的行数没变、库存没变、购物袋还在，
不是断言日志或返回值——只有行数能证明闸门真的拦住了。

金额在卡片上就摊开成四行（小计 / 优惠 / 运费 / **应付**），用户看到的就是将要被收走的那个数。
订单落库后同样存四列，且 `total` 与 `pay_amount` 在同一条 INSERT 里用同一个值写入、写后不可变
——「历史列 = 应付」这条不变量因此不可能漂移，也就能被 SQL 断言直接检查。

**幂等键由服务端生成**（`ord-<32hex>`）并随待确认记录落库。这不是防御性冗余：
工具参数是模型填的，只要键有传值入口，就能被构造出来绕过防重；
把入口堵死在物理上，比在提示词里叮嘱「不要乱填」可靠得多。

确认的执行顺序也值得说一句：**落单与清袋在同一个事务里**。两者都是本地数据库写，
原子化成本极低；分开就会出现「订单已生成、袋子里东西还在」的幽灵袋。
（对照：支付与发消息是外部调用，必须移出长事务，见
[并发隔离与异步设计](并发隔离与异步设计.md)。）
