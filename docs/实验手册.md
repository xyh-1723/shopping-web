# 实验手册：用操作验证，而不是只记概念

先在项目根目录启动商城并用 `student` 登录。自动化测试使用自己的数据库；浏览器实验会改变当前商城的订单与库存。需要新的练习数据时，停止服务，再为 jar 指定另一个文件路径，例如 `--spring.datasource.url=jdbc:h2:file:./data/practice2`。不要同时打开两个进程操作同一个 H2 文件库。

## 实验 1：一条完整业务链路（约 10 分钟）

1. 在首页用分类按钮筛选，再搜索“杯”。
2. 加入一个马克杯和一本笔记本，观察购物袋金额是 68 元。
3. 提交订单，记下订单编号，确认待支付。
4. 点击“重发上次下单请求”。预期：仍是原编号，订单数不增加。
5. 模拟支付。预期：PAID，页面说明没有真实扣款。
6. 打开消息中心，稍等 1–3 秒。预期：出现创建和支付通知，投递状态为已送达。
7. 再下一份新订单，然后取消。预期：库存恢复，重复取消接口也不会多恢复。

源码路线：`OrderController → OrderFacade → OrderTransactions → ProductCatalog / DomainEventPublisher`。

## 实验 2：会话、CSRF 和接口调用

在**已登录的商城首页**打开浏览器开发者工具 Console，执行下面的辅助代码（用于后续实验）：

```javascript
window.mallLab = {
  key: crypto.randomUUID(),
  body: { items: [{ productId: 1, quantity: 1 }] },
  async request(path, body, key) {
    const csrf = document.querySelector('meta[name="_csrf"]')?.content;
    const header = document.querySelector('meta[name="_csrf_header"]')?.content;
    const response = await fetch(path, {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        [header]: csrf,
        ...(key ? { "Idempotency-Key": key } : {}),
      },
      body: body ? JSON.stringify(body) : undefined,
    });
    const text = await response.text();
    console.log(response.status, text ? JSON.parse(text) : null);
    return text ? JSON.parse(text) : null;
  },
};
```

辅助代码只保存在当前页面内存；刷新或跳到学习地图后需要回首页重新执行。它不会绕过登录或安全校验。

发送一份不带 token 的 POST：

```javascript
await fetch("/api/orders", { method: "POST" }).then((r) => r.status);
```

预期为 403。补上正确 token 后才进入 MVC 层。登出后读取 `/api/orders` 会得到 401。

## 实验 3：幂等重放与正文冲突

沿用上面的 mallLab：

```javascript
window.labOrder = await mallLab.request(
  "/api/orders",
  mallLab.body,
  mallLab.key,
);
await mallLab.request("/api/orders", mallLab.body, mallLab.key);
await mallLab.request(
  "/api/orders",
  { items: [{ productId: 1, quantity: 2 }] },
  mallLab.key,
);
```

预期：前两次 200 且 id 一致，第三次 409 `IDEMPOTENCY_CONFLICT`。把 items 顺序调换不影响指纹；同一商品重复出现则返回 400。

保存原订单后可以继续测试支付幂等：

```javascript
await mallLab.request(`/api/orders/${labOrder.id}/pay`, {
  method: "DEMO_CARD",
});
await mallLab.request(`/api/orders/${labOrder.id}/pay`, {
  method: "DEMO_CARD",
});
await mallLab.request(`/api/orders/${labOrder.id}/pay`, {
  method: "DEMO_WALLET",
});
```

前两次同流水，第三次支付方式冲突。这个订单再取消也会得到 409。

思考：网络超时后新建一个 key 重试，会不会造成第二份订单？会。因此客户端需要保留原 key 和原正文，而不是仅仅后端实现一个“幂等注解”。

## 实验 4：输入错误与事务回滚

```javascript
await mallLab.request(
  "/api/orders",
  { items: [{ productId: 1, quantity: 0 }] },
  crypto.randomUUID(),
);
```

预期 400，数据库没有新订单。

运行针对第二件商品不足的自动化实验：

```powershell
mvn '-Dtest=MallIntegrationTest#insufficientSecondProductRollsBackEarlierDeductionAndOrder' test
```

测试先设定商品 2 库存为 0，再购买商品 1 和 2。断言商品 1 库存不变、订单和事件都没有留下。打开测试方法，看每一个断言对应哪个业务承诺。

继续运行：

```powershell
mvn '-Dtest=MallIntegrationTest#outboxWriteFailureRollsBackBusinessTransaction' test
```

预期模拟事件表失败后，库存和订单也回滚。由此理解 Outbox 为什么必须和订单放在同一事务中。

## 实验 5：并发，不靠手速双击

分别运行：

```powershell
mvn '-Dtest=MallIntegrationTest#concurrentDuplicateRequestsProduceOneOrder' test
mvn '-Dtest=MallIntegrationTest#competingRequestsCannotOversell' test
mvn '-Dtest=MallIntegrationTest#paymentAndCancellationRaceHasOneWinner' test
mvn '-Dtest=MallIntegrationTest#concurrentCancellationsRestoreStockOnlyOnce' test
```

预期：

| 场景                     | 验收结果                         |
| ------------------------ | -------------------------------- |
| 16 个相同 key 的并发请求 | 1 份订单、1 次扣减、1 条创建事件 |
| 24 个新请求抢 7 件库存   | 7 成功、17 库存不足，库存为 0    |
| 支付和取消竞争           | 只有一个终态获胜，库存与终态一致 |
| 12 次并发取消            | 库存只归还一次                   |

测试使用 CountDownLatch 同时放行，不依赖 `Thread.sleep` 碰运气。IDE 中可以同时观察多个工作线程，但断点暂停会改变竞争时序；最终仍以不带断点的测试结果判断。

## 实验 6：AOP 和异步线程

默认日志里查找：

```text
operation=create-order-transaction ... thread=http-nio-8080-exec-...
operation=consume-event ... thread=mall-message-...
```

这说明 HTTP 请求和通知在不同线程执行。切面是统一实现，不是在每个业务方法内重复计时。

将 `@Observed` 临时从一个方法移除后，该方法不再输出对应计时日志，但核心业务规则应该仍能执行。练习结束恢复源码，再运行测试。

## 实验 7：故障 → 重试 → 死信 → 恢复

推荐用 jar，便于明确设置启动参数。先完成 `mvn package`，停止当前商城，再启动：

```powershell
java -jar target/learning-mall-1.0.0.jar --mall.messaging.simulate-failure=true
```

1. 登录并下单。订单仍成功，因为当前故障发生在消费通知时，不在保存 Outbox 时。
2. 打开消息中心。看到 PENDING、失败次数增加，错误为 `IllegalStateException`。
3. 默认第 1 次消费约 1 秒开始；之后间隔约 2/4/8/16 秒，计入扫描误差，通常约 35–45 秒内看到 DEAD。
4. 此时通知列表没有这条事件的成功通知；订单仍存在。
5. 停止进程，去掉故障参数重新启动相同数据库。
6. 登录后在 DEAD 事件上点击“重新投递”。预期状态变为 PENDING 再到 DELIVERED，生成一条通知，失败计数从新一轮的 0 开始。

也可以通过环境变量 `MALL_MESSAGING_SIMULATE_FAILURE=true` 打开开关；恢复时要删除/设 false 后重启。只刷新浏览器不会修改服务端启动配置。

如果希望快速自动验证而不等待，执行 `retryBackoffDeadLetterAndOwnerReplay` 测试。它会在测试数据库中控制 next_attempt_at，不改变生产代码的重试间隔。

## 实验 8：未投递消息跨重启保留

启动时设置 `--mall.messaging.enabled=false`，创建一笔订单。此时事件保存为 PENDING，但消费者不调度。停止服务，使用原数据路径重新启动并移除此参数。预期事件随后送达。

自动验证：

```shell
mvn -Dtest=RestartPersistenceTest test
```

测试会真正关闭并重建应用上下文、重新打开文件数据库，同时验证同 key 重发没有重复订单或扣库存。它不会覆盖当前商城的数据文件。

## 实验 9：线程池饱和

```shell
mvn -Dtest=DispatcherBackpressureTest test
```

测试使用核心 1、最大 1、队列 1。先阻塞正在执行的任务，再填满队列，然后调度事件。第一次提交被拒绝；释放容量后，同一事件仍可被调度。读懂这个测试，你就能解释为什么不能在“刚放入内存队列”时把事件当成已送达。

## 实验 10：用户隔离

先用 student 创建订单并复制编号，退出，改用 classmate 登录。在控制台查询：

```javascript
await fetch("/api/orders/替换为student的订单编号").then((r) => r.status);
```

预期 404。classmate 的订单和通知列表里也没有 student 的记录。界面上藏起按钮不是权限保护，后端查询中的 username 才是关键之一。

- 我能画出一次下单的 Controller/Service/Repository 调用链。
- 我能指出真正防止重复订单的唯一约束，而不只说“先查询”。
- 我能解释为什么事务、幂等、防超卖是相关但不同的三个问题。
- 我知道当前支付是本地模拟，消息不是独立 MQ，外部副作用需要额外设计。
- 我能看懂一个失败测试并找到它验证的业务不变量。
