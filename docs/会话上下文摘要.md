## 一、项目是什么

`springboot-learning-mall`：一个把**电商核心链路**与**LLM Agent 工程**放在同一个 Spring Boot 应用里、
用真实测试与真机冒烟把设计决策钉死的教学项目。目标对标「淘宝级专业 agent」。

规模：`src/main/java` 130 个类，`src` 共 1.5 万行 Java，26 个测试类，**272 个测试全绿**，
Flyway 迁移 V1–**V13**。

## 三、五条项目级设计决策（最容易忘记、忘了就会做错）

1. **状态变更一律带前置条件**：`UPDATE ... WHERE id=? AND status='PENDING'`，
   影响行数 = 1 才表示「这次是我改的」，才有权做后续副作用（释放库存等）。
   **幂等来自条件更新，不来自「先查再决定」。** 这条在订单关单里落地。
2. **安全关键逻辑只有一份实现**：关单动作（`OrderTransactions.close`）、进度回调容错
   （`TurnListener.safely`）、增量输出守卫。复制第二份就是分叉的开始。
3. **新增枚举值优先不动 `CHECK` 约束**：V1 的 status 是内联 CHECK，
   H2 自动起名 `CONSTRAINT_x` 这类形式，**写进迁移跨环境会失配**（已用 h2 Shell 实测确认）。
   所以「超时关闭」用 `close_reason` 而非第四态 `CLOSED`。
4. **可选功能缺配置只降级、不拖垮启动**：`AssistantConfig` 用自定义 `@Conditional`
   （`VisionApiKeyPresentCondition`）而非 `@ConditionalOnExpression`——后者在缺 `api-key` 时
   抛异常导致**整个应用起不来**。
5. **定时扫描不照抄上次游标**：判断依据是「处理之后这行还会不会被再次选中」。
   到期订单被关掉后自然离开结果集 → 队列收敛，不需要额外游标。
   反之，主动服务扫描**必须**推进游标（否则暂时不需要提醒的行占住队首，队尾永久饥饿）。
6. **金额只有一处算法，且订单不能自己算**：`dev.learning.mall.pricing` 包的 `Pricer`
   是唯一的金额入口，业务代码里出现 `BigDecimal::add` 裸求和就是 bug。
   `total` 与 `pay_amount` 在同一条 INSERT 里用同一个值写入、写后不可变——
   这样「历史列 = 应付」才不可能漂移，也才能被 SQL 断言直接检查。
7. **服务端生成幂等键，模型没有传值入口**：助手下单的 `idempotency_key` 是
   `ord-<32hex>`，由服务端生成并落库。工具参数是模型填的，只要有入口就能被构造出来绕过防重。
8. **HITL 泛化而不是新建表**：`assistant_pending_action` 靠 `kind` 分支
   （`ORDER_PAYMENT` / `ORDER_CREATE` / `ORDER_CANCEL`），归属校验、一次性原子迁移、TTL、审计
   只有一份实现。**支付路径的审计码必须保持 `HITL_PAY_*` 逐字不变**——改掉会让最有风险的
   链路从监控里消失。

## 四、方法论（本项目一直在用，别丢）

- **反向验证**：写完测试后把实现临时改回旧写法，确认测试**变红**；不变红说明测试在测别的地方。
  本项目已**三次**靠它发现问题，其中两次是「全绿」——最有价值的两条教训：
  - 第一次（订单关单）：测试碰不到关单动作自身的规则 → 补直击动作本身的用例；
  - 第三次（HITL 一次性迁移）：串行重复确认被**预检**拦住，根本走不到原子迁移 →
    「不变红」不代表测试没用，**可能只是你测的是另一层**。一次性迁移真正防的是**并发**，
    必须写多线程用例才验得到。
- **测试也会替 bug 站岗**：257 全绿里有一条断言（订单金额 78.00）锁住的正是待修的 bug。
  数字来源可疑时，先问「这个期望值是怎么来的」。
- **先论证再动手**：加任何机制（如提醒冷却）之前，先确认它要解决的问题是不是已经被解决了。
  已因此移除两项伪需求（购物车乐观锁、提醒时间冷却）。
- **不可信输入新入口必须过校验**：图片走文件头魔数嗅探，不信客户端声明的 MIME。

## 六、环境坑（直接绕，别重新踩）

1. **本机 HTTP 代理 `http_proxy=127.0.0.1:3431` 会让 localhost 返回 502。**
   访问本地服务一律 `curl --noproxy '*'` / `NO_PROXY='*'`。
2. **`nohup java -jar ... &` 起的进程会随 Bash 会话结束被回收**，下一句命令时服务已经没了。
   要用工具的后台任务方式启动。
3. **本仓库没有 `mvnw`**，用系统 `mvn`（`D:\java-tool\apache-maven-3.9.14`）。
   跑真机冒烟前先 `cp data/mall.mv.db` 备份。

### 9.2 P2-1 的定位已被换掉

- 原定位：服务端搜索/排序/分页下推 SQL（理由是商品 > 200 会慢）→ **实测证伪**，属伪需求一类。
- 新定位：**服务端强制的返回结果上限** + 截断后如何不误导用户（模型可能把「前 N 件」说成「只有这几件」）。
- 同一个类里 `recommendByBudget` 有 `.limit(5)`、`searchProducts` 没有——是漏了，不是取舍。
- SQL 下推降级为可选（几百件下收益是毫秒级）。

### 9.6 修正：9.2 的「token 问题」结论是错的（勿再引用）

我差点重复造轮子。**`AgentLoop` 已经有工具结果截断，P2-1 的 token 问题不存在。**

- `AgentLoop` L475：`truncate(execution.text(), budget.maxToolResultChars())`

即 16505 字符在进模型前**已截到 4000**，且附带截断告知——「模型误以为只有这几件」这个风险，那段提示文案就是专门防它的。

**教训（方法论，务必记住）**：我的基准直接调 `CatalogTools.searchProducts()`，**绕过了 `AgentLoop` 那一层**，
