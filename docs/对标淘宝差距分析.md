# 对标淘宝：能力差距分析与需求池

> 角色：产品经理（许清楚 / Alice）｜日期：2026-10-16
> 对象：`springboot-learning-mall`（128 个类 / 257 个测试 / Flyway V1–V11）
> 口径：**这是教学项目，不是要重写成淘宝。** 本文只回答一个问题——
> 「离『淘宝级专业 agent』还差什么，其中哪些现在就该补」。

---

## 一、执行摘要

**一句话结论**：项目的**工程内核（幂等、状态机、可靠异步、Agent Harness、安全闸门）已经达到专业水准，甚至超过很多生产系统**；
真正掉队的是**两条端到端的「最后一公里」**——**金额在下单那一刻断了口径**，和 **Agent 在下单那一刻断了手**。
这两条恰好都在用户能直接摸到的地方，且都不需要新架构，只需要把已有的东西接上。

| # | 结论 | 依据 |
| - | ---- | ---- |
| 1 | **订单金额与「购物袋 / 助手报价」不是同一个数。** `CartPricing` 算了满减与运费，但下单路径（`OrderTransactions.create`）**自己裸求和**，从不调用它。买 1 个机械键盘：购物袋显示应付 ¥174（满 199 减 25、包邮），订单金额 ¥199，**差 ¥25**。这是数据正确性缺陷，不是体验瑕疵。 | `OrderTransactions.create` L46–47 / L53 vs `CartPricing.quote`；`application.yml` `mall.shopping` 已生效；订单包无任何 `cart` 引用（已 grep 确认） |
| 2 | **导购闭环缺最后一环：助手不能下单。** 工具包里有「加购 / 改量 / 移除 / 清空 / 发起支付」，唯独没有「提交订单」；而 `requestPayment` 只能对**已存在的订单**发起。用户说「帮我买下」→ 助手加完购，只能让用户自己去页面点。 | `ToolRegistry.forActor` 工具清单；`CartTools`（4 个工具，无 createOrder）；`PaymentTools.requestPayment(username, orderId, method)` |
| 3 | **文档承诺的架构，代码没实现。** `docs/导购闭环与记忆.md` 画了「购物袋页面 / 下单结算 / 助手对话 → 同一个 `CartPricing.quote()`」，`ShoppingProperties` 的注释写着「『对话里承诺 10 元、结算只减 5 元』这类事故**在结构上不可能发生**」。这两句话目前是假的——而 257 个测试没抓到，因为购物袋测试与订单测试各测各的。 | `docs/导购闭环与记忆.md` L28–36；`ShoppingProperties` 类注释；`application.yml` `mall.shopping` 注释 |
| 4 | **「缺 Kafka / 缺后台 / 缺物流」不是差距，是取舍。** 真正需要盯的是另一件事：主动提醒（`mall_alert`）**没有投递保障**——没重试、没死信、没投递记录。站内信场景下无感，**一旦要做邮件/短信外发，它会静默丢消息且查不到**。 | V8 迁移注释明确论证过「为什么不复用 outbox」；`docs/接口与数据结构.md` L401–403 |
| 5 | **离「淘宝级」最近的一步，不是加更多工具，是补上断了的那一步。** 现有 10 个工具包里 8 个是只读或低风险写，能推进交易的只有「加购」和「发起支付」，中间的「下单」是空的。补一个工具 > 加十个查询工具。 | 同上 |

**整体判断**：工程深度 ≈ 生产级，端到端完整度 ≈ 演示级。差的不是能力，是**把能力连成一条用户能走完的路**。

## 三、差距清单

**严重度定义**

- `阻断` = 不补就不能叫「专业」。不是"体验差一点"，是**数据错的**或**核心承诺没兑现**。
- `明显` = 用户能感觉到，但系统仍然自洽。
- `锦上添花` = 用户当下无感，主要是运营侧 / 排障侧的收益。

**归类定义**：`该补` / `规模才需要`（附触发阈值）/ `本项目刻意不做`（教学边界）

---

### G1　下单金额绕过了唯一计算入口：满减与运费进了购物袋，没进订单

- **用户能感觉到吗**：**能，而且是立刻、每次、按钱算。**
- **严重度**：`阻断`
- **归类**：`该补`
- **当前症状（可复现）**

  | 场景 | 购物袋显示应付 | 订单金额 | 差 |
  | ---- | -------------- | -------- | -- |
  | 机械键盘 ×1（¥199） | ¥174（满199减25 + 包邮） | **¥199** | **+¥25（用户多付）** |
  | 云朵马克杯 ×2（¥78） | ¥86（不满99，+运费8） | **¥78** | **−¥8（用户少付）** |

  两个方向都会错，所以「用户占便宜/吃亏」都有可能，无法用一句文案糊过去。
  助手路径同样错：`viewCart` 报 ¥174 → 用户去下单 → 订单 ¥199 → 支付确认卡片显示 ¥199。

- **证据**
  - `OrderTransactions.create` L46–47：`total = Σ(unitPrice × quantity)`，裸求和；L53 `orders.insert(..., total, ...)`。
  - `OrderRepository.insert` L58：`INSERT INTO mall_order(..., total, ...)` —— `V1__create_mall.sql` 里 `mall_order` 只有 `total` 一列，**没有 `subtotal` / `discount` / `shipping_fee`**。
  - `grep -rn "cart" src/main/java/dev/learning/mall/order/` → **零命中**，订单包完全不认识购物袋与定价。
  - 反面对照：`CartPricing.quote`（满减取最高档 → 折后判断包邮 → 加运费 → 凑单提示）只被 `CartService` 调用（`grep CartPricing` 仅命中 `CartService`）。
  - `application.yml` 的 `mall.shopping` 规则**已生效**（99 包邮 / 运费 8 / 满99减10 / 满199减25）；同文件注释却写着「购物袋页面、下单、助手对话三处共用」——注释与代码不符。
  - 前端对照：`app.js` L145–150 取 `cartView.total`，L348 订单卡片取 `order.total` —— 同一个用户在 3 秒内看到两个不同的数。

- **为什么测试没抓到**：`ShoppingCartTest` 测 `CartService`，订单测试自己构造 `lines`。**两条链路没有一条共同断言。**

### G2　Agent 写操作断在「加购」与「支付」之间：助手不能下单、不能取消订单

- **用户能感觉到吗**：**能。** 用户说「帮我把袋子里的买了」→ 助手加完购，然后让用户自己去页面点提交；说「那单我不要了」→ 助手只能说「请去订单页操作」。
- **严重度**：`阻断`
- **归类**：`该补`
- **当前症状（可复现）**
  - 打开 `/assistant`，让助手加购并说「帮我下单」：助手会调用 `viewCart` 报出金额，然后**没有任何工具可用**（`ToolRegistry.forActor` 注册了 `catalogTools` / `guideTools` / `proactiveTools` / `customerTools` / `memoryTools` / `cartTools` / `watchTools` / `knowledgeTools` / `paymentTools` / `staffTools`，逐个看：`CartTools` 只有 `addToCart` / `setCartQuantity` / `removeFromCart` / `clearCart`，**没有 createOrder**）。
  - `PaymentTools.requestPayment(username, orderId, method)` 的 `orderId` **只能来自既有订单**，而创建订单的唯一入口是页面 `POST /api/orders`（`OrderController` L17–19）。
  - `CustomerTools` 只有 `myOrders`（只读），无取消。
  - `docs/导购闭环与记忆.md` 标题就是「导购闭环」，但闭环的**成交那一跳不在闭环里**。

- **证据**：`ToolRegistry.forActor` L89–115；`CartTools` L42–72；`PaymentTools` L36–41；`CustomerTools` L29–30。

---

### G3　文档承诺的架构与代码不一致，且无跨模块守护

- **用户能感觉到吗**：**不能直接感觉到**——但它是 G1 长期存在且未被发现的**根因**。
- **严重度**：`阻断`（作为流程缺陷）
- **归类**：`该补`
- **当前症状**
  - `docs/导购闭环与记忆.md` L28–36 声称三处共用 `CartPricing.quote()`，L14 表格写「金额：结算金额与页面完全一致 ✅」。
  - `ShoppingProperties` 类注释：「『对话里承诺 10 元、结算只减 5 元』这类事故**在结构上不可能发生**」。
  - 事实：结构上完全可能发生，且正在发生（见 G1）。
  - 项目有一流的方法论（反向验证、先论证再动手），但它**只用在单个模块内部**，没有用于「架构承诺 → 跨模块断言」。

### G4　已支付订单是终态：无退款、无售后、无「反悔」路径

- **用户能感觉到吗**：**能。** 付完款想取消 → `OrderTransactions.cancel` L89 直接抛 `INVALID_STATE`「已支付订单不能取消」，页面连按钮都没有。
- **严重度**：`明显`
- **归类**：`该补`（最小状态机）/ `本项目刻意不做`（完整售后流程：退货物流、平台介入）
- **当前症状**
  - `mall_order.status` 只有 `PENDING / PAID / CANCELLED`，`PAID` 之后**没有任何出边**。
  - `mall_order` 无 `paid_at`、无 `refund_*` 字段；V1–V11 无退款表。
  - 助手侧更尴尬：`KnowledgeTools` 的工具说明写着「当用户询问商城规则、**售后服务**、商品评价……时使用」——助手能**讲**售后政策（RAG 命中知识库文档），但**办不了**任何一件事。**说得到做不到，比不说更伤信任。**
- **证据**：`OrderTransactions.cancel` L86–92；`V1__create_mall.sql` L16 状态 CHECK；`KnowledgeTools` L37。
- **注**：真实退款涉及资金与《网络交易监督管理办法》等规则，本文只主张**状态机与申请入口**，不主张接真实资金。合规口径见「待确认问题」。

---

### G5　商品检索全部在浏览器内存：无服务端搜索、排序、分页

- **用户能感觉到吗**：**当前不能**（6 件商品，前端过滤瞬时完成）。
- **严重度**：`锦上添花`（当下）→ `明显`（规模上来后）
- **归类**：`规模才需要`。**触发阈值**：商品数 > 约 200 件（前端一次拉全量的响应体开始可感知），或需要「服务端排序 / 个性化重排 / 结果数上限」（任一条成立就该做）。
- **当前症状（可验证）**
  - `ProductRepository.list()` = `SELECT * FROM product ORDER BY id`，**无 WHERE、无 LIMIT**。
  - `ProductController` 只有 `GET /api/products`（全量）与 `GET /api/products/{id}`，**没有 keyword / category / sort / page 参数**。
  - 前端 `app.js` L103–107：`.filter()` 在浏览器里做关键词与分类过滤。
  - Agent 侧同样：`CatalogTools.searchProducts` 调 `catalog.list()` 后**在 Java 里 stream 过滤**。
- **证据**：`ProductRepository` L13；`ProductController` L18–19；`app.js` L103–107；`CatalogTools` L29–40。

---

### G6　库存无变动流水：改了库存，没人知道是谁、什么时候、为什么改的

- **用户能感觉到吗**：**间接地能**。店员把某件商品库存从 30 改成 5，第二天没人能回答「为什么」；助手的 `inventoryAlerts` 只能说「低于阈值、建议补货」，**说不出「是因为 3 分钟前有人下了 2 单」**。
- **严重度**：`明显`
- **归类**：`该补`
- **当前症状（可验证）**
  - `ProductRepository` 的 `deduct` / `restore` / `setStock` 全都是**直接 `UPDATE product SET stock = ...`**，无旁路记录。
  - V1–V11 **没有任何 ledger / journal 表**（已核对全部 11 个迁移文件）。
  - `SecurityConfig` L37–38 只做了角色校验（`hasRole("STAFF")`），**不落审计**；`assistant_audit` 只记 LLM 安全事件，**不记经营动作**。
  - 后果：`inventoryAlerts`（`StaffTools` L52–53）给出的「补货建议」没有数据支撑，只能靠阈值硬编码。
- **教学价值**：流水表（谁/何时/业务类型/变化量/前后值/关联订单号）是「对账思维」的最小载体，比再优化一次防超卖并发更有教学密度。

---

### G7　实物库存与可用库存是同一个数字，预占与实物互相污染

- **用户能感觉到吗**：**能，但只在特定操作序列下。** 用户 A 下单预占 2 件（stock 30→28），店员此时用 `POST /api/products/{id}/stock` 直接把库存**设为 30**（补货语义），A 的订单超时关闭时 `release` 无条件 `stock = stock + 2` → **库存变成 32，凭空多出 2 件**。
- **严重度**：`明显`
- **归类**：`该补`（低成本：把「补货」改成增量语义或加 `reserved` 列）/ `规模才需要`（完整的可用库存服务 + 分仓）
- **当前症状（可验证）**
  - `product.stock` 一个字段同时承担三种语义：实物库存、可售库存、已扣减后余量。
  - `updateStock` 是**绝对值设置**（`setStock`），不是增量；与「预占」语义天然冲突。
  - `restore` 是**无条件** `stock = stock + qty`，没有上限校验（对比 `deduct` 有 `AND stock >= qty` 的条件，两者不对称）。
- **证据**：`ProductRepository` L22–30；`ProductService.updateStock` L62–74；`OrderTransactions.close` L126。

### G8　触达只有站内信，而且表结构撑不住外发

- **用户能感觉到吗**：**能。** 关掉浏览器就收不到任何提醒；弃单召回的「东西还在，记得回来」只躺在站内信里，用户不打开就永远看不到。
- **严重度**：`明显`
- **归类**：`该补`（外发通道抽象 + 退订位）/ `规模才需要`（接真实服务商）
- **当前症状（可验证）**
  - `notification` 表：`event_id` 主键 + `content`，**无通道字段、无送达状态、无已读回执**（`read_at` 只存在于 `mall_alert`，`notification` 连它都没有）。
  - `mall_alert`：**写入即视为送达**——无重试、无死信、无投递记录。站内信场景下成立（读一次就没了），但这是**唯一一条没有投递保障的链路**。
  - `docs/验证记录.md` L481 已自认：「召回目前只到站内提醒；外发通道（邮件/短信）需凭据与退订机制，涉合规，未做。」
- **合规提醒（不编造条文，仅提示需要确认的口径）**：一旦外发短信/邮件，涉及《个人信息保护法》的告知同意与最小必要，以及短信服务商的退订与时限要求。**这些需在动手前由主理人/用户确认口径，本文不替法务下结论。**

### G9　无收货地址、无买家信息、无账户体系

- **用户能感觉到吗**：**当前不能**（无物流、无真实交易）。
- **严重度**：`锦上添花`

## 四、需求池

> 语言约定：**must** = 不做完不算完成；**should** = 强烈建议；**could** = 有余力再做。
> 每条都给可度量验收标准。

### P0（Must have）—— 不补就不能叫「专业」

#### P0-1　下单金额必须与购物袋 / 助手报价完全一致，并落库明细

- 下单路径 **must** 调用 `CartPricing.quote()` 计算金额，**不得**在 `OrderTransactions` 内自行求和。
- 新增迁移 V12，**must** 为 `mall_order` 增加 `subtotal` / `discount` / `shipping_fee` / `pay_amount` 四列；`total` 保留为 `pay_amount` 的兼容别名（避免破坏现有 257 个测试）。
- 迁移 **must** 回填存量订单：`subtotal = total, discount = 0, shipping_fee = 0`。
- `OrderView` **must** 暴露这四项；订单卡片 **must** 展示「小计 / 优惠 / 运费 / 应付」四行。
- **验收标准（可度量）**
  1. 跨模块断言：对同一组行，`GET /api/cart` 的 `total` 与 `POST /api/orders` 的 `pay_amount` **差值必须为 0**（误差 0 分）。至少覆盖 3 组：① 满减未命中且含运费（¥78 → ¥86）② 满减命中且包邮（¥199 → ¥174）③ 恰好卡门槛（¥99）。
  2. **反向验证必须变红**：把 `create` 临时改回裸求和，上述断言 **must fail**。不变红说明断言没测到点上（本项目已有两次被这条救回的先例）。
  3. 助手侧：`viewCart` 报出的数字与随后下单的 `pay_amount` 一致，误差 0。
  4. 257 个既有测试保持全绿。

#### P0-2　Agent 必须能完成下单闭环（工具 + HITL + 幂等）

- **must** 新增「提交订单」工具，走**与页面完全相同**的 `OrderFacade.create`（不得另写一份下单实现——项目决策第 2 条：安全关键逻辑只有一份实现）。
- **must** 纳入 human-in-the-loop：下单会占用库存，风险高于加购（不可逆程度低于支付但高于加购）。确认卡片 **must** 显示**服务端算出的应付金额**（承接 P0-1）。
- **must** 自带幂等键生成策略（服务端生成并回传，不依赖模型传 UUID）。
- **should** 同时提供「取消订单」工具，同样走 HITL（取消不可撤销）。
- **验收标准（可度量）**
  1. 端到端：对话中说「帮我买下袋子里的东西」→ 产生一条待确认卡片 → 用户确认 → `mall_order` 新增 1 行，`stock` 按量扣减，**库存差值可断言**。
  2. 未确认时 `mall_order` **必须保持 0 新增行**（断言数据库行数，不是断言日志）。
  3. 重复确认同一待确认卡片 **must** 只产生 1 笔订单（复用 `Idempotency-Key`）。
  4. 普通顾客账号 **must** 拿不到任何越权路径；`ToolRegistry.userToolBundleExcludesStaffTools` 一类测试继续守住角色边界。
  5. 助手不得在用户确认前声称「已下单」（既有 `requestPayment` 的提示词约定 must 平移过来）。

#### P0-3　为「架构承诺」建立跨模块守护

- **must** 为每一条写进文档的「结构性保证」配一条**跨模块的**断言测试，而非只测单模块内部。
- **验收标准**：至少补齐「金额单一口径」这一条（见 P0-1 验收 1、2）；并在 `docs/导购闭环与记忆.md` 中把目前不成立的承诺**修正为实际状态**（文档与代码不一致时，改的是哪个要先说清楚）。

### P1（Should have）—— 用户能察觉，或直接影响可信度

#### P1-1　库存变动流水

- **should** 新增 `stock_ledger` 表：`product_id` / `change` / `before` / `after` / `reason`（`RESERVE` / `RELEASE` / `RESTOCK` / `MANUAL`）/ `order_id` / `operator` / `created_at`。
- `deduct` / `restore` / `setStock` **must** 在同一事务内写流水（不写流水的库存变更 should 视为不合法路径）。
- **验收标准**：店员改库存后，可按商品查出完整变动序列，「当前库存 = 初始库存 + Σ(change)」恒等成立；助手 `inventoryAlerts` 的补货建议 **must** 引用真实的近期变动（而非仅阈值）。

#### P1-2　支付后状态机的最小延伸

- **should** 至少支持「已支付 → 退款中 → 已退款」的状态与申请入口，使「付完款想反悔」有一条明确路径。
- **must not** 在此阶段引入真实资金结算。
- **验收标准**：对已支付订单发起退款申请后状态转为 `REFUNDING`，重复申请幂等；未支付的订单**不得**进入退款流程（断言 409 + 明确文案，不能是「未知错误」）。
- **依赖**：待确认问题 Q3 拍板后再启动。

#### P1-3　可观测：指标与积压

- **should** 引入 Micrometer，暴露至少 4 个助手侧指标：**首字延迟（P95）**、**工具调用成功率（按工具名）**、**单轮停止原因分布**、**超时关单每轮积压数**。
- **should** 把 `management.endpoints` 从 `health,info` 扩到含 `metrics`（本地学习环境可访问）。
- **验收标准**：无需进应用内部即可读到上述 4 个数；关单积压 > 0 时能在指标上看到（配合既有 `auto-close-max-per-scan: 200`）。

#### P1-4　提醒外发通道抽象（先定接口，不接服务商）

- **should** 定义 `NotificationChannel` 抽象与「已读/已送达/退订」三个状态位，**先不接真实邮件/短信服务商**。
- **must** 为 `mall_alert` / `notification` 补上通道与状态字段，使「外发是否成功」可被查询——这是 G8 的真正内核（**当前表结构撑不住外发**）。
- **验收标准**：站内信路径行为不变（既有测试全绿）；模拟一个会失败的通道，失败**必须可查**（有状态、有次数、有最后错误），不得静默丢弃。
- **依赖**：待确认问题 Q5（合规口径）先拍板。

#### P1-5　价格变动提示

- **should** 在下单前比对「用户看到的金额」与「服务端当前金额」，不一致时返回明确错误码（如 `PRICE_CHANGED`）并附带新金额，由前端/助手重新确认。
- **验收标准**：加购后改价再下单 → 409 `PRICE_CHANGED` + 新金额；用户按新金额重新提交 **must** 成功，且金额与新报价一致（误差 0）。

#### P1-6　订单成功后清空服务端购物袋（服务端保证）

- **验收标准**：直接 `POST /api/orders` 成功后，该用户 `mall_cart_item` 行数 **must** 为 0。

## 五、反直觉洞察

### 洞察 1：看起来该做「换 MQ」，其实不该做；看起来「已有 outbox 就够了」，其实只解决了一半

`outbox_event` 的 `aggregate_id` 外键指向 `mall_order(id)`（V8 注释论证过为什么不把它改成可空——**这是一次正确的取舍，不是缺陷**）。所以：

- 订单事件：有「必须送达 + 重试 + 退避 + 死信 + 重启恢复」，**这条链路是完整的**。
- 主动提醒（`mall_alert`）：**写入即视为送达**，无重试、无死信、无投递记录。

站内信场景下这个设计是对的（读一次就没了，不需要投递保障）。**但一旦 P1-4 要外发，`mall_alert` 会静默丢消息，而且丢了你查不到。**
所以真正的待办**不是**「引入 Kafka/RabbitMQ」，而是「**决定 `mall_alert` 要不要升级成第二条可靠投递链路**」——这是一次建模决策，不是一次中间件替换。先换 MQ 的人，会在错误的地方花掉全部预算。

### 洞察 2：项目写得最漂亮的那段架构，恰恰是唯一没被测试守住的那段

`CartPricing` + `ShoppingProperties` + 文档里的三入口示意图，是全项目最能体现「工程判断」的一段设计：**用结构消除事故，而不是用提示词叮嘱模型别算错。** 这段设计值得满分。

但它**只接了两根线中的一根**（购物袋页面、助手对话），第三根（下单结算）没接。更值得警惕的是：**257 个测试全绿**。原因是购物袋测试和订单测试各测各的，**从来没有一条断言同时走过这两条链路**。

教训（建议写进方法论第 4 条）：**越是写进文档的架构承诺，越需要跨模块的断言来守住。单模块内的反向验证再严格，也照不到模块与模块之间那条边。**

### 洞察 3：给助手加更多工具不是当前瓶颈，补上「下单」比加十个只读工具更有价值

现有 10 个工具包，能力清单看起来很全。但按「能不能推进交易」一分类就露馅了：

| 能不能推进交易 | 工具 |
| -------------- | ---- |
| 能（写） | `addToCart` / `setCartQuantity` / `removeFromCart` / `clearCart` / `requestPayment` |
| 不能（只读） | `searchProducts` / `recommendByBudget` / `getProduct` / `viewCart` / `compareProducts` / `myOrders` / `myWatches` / `myAlerts` / `recommendRelated` / 知识库检索 / 店员三件套 |

**能推进交易的只有 5 个，且中间那一步（下单）是空的。** 用户体感是「说到一半让我自己去做」。
Agent 的能力边界不是工具数量，是**能不能完成用户交给它的那件事**。补一个 `createOrder`，价值高于再加十个查询工具。

### 洞察 4：库存流水比再优化一次并发更值得先做

防超卖这一块已经做得很扎实：条件 UPDATE（`WHERE stock >= qty`）、固定加锁顺序、影响行数即幂等。**再往深挖并发，边际收益很小。**

但「这件货为什么少了 3 件」**完全回答不了**——没有任何流水表，店员改库存也不落审计。而 `inventoryAlerts` 这个店员工具，恰好卡在这里：它能说「低于阈值、建议补货」，说不出「因为 3 分钟前有人下了 2 单」。
**一个只能报警不能归因的运营工具，用户用两次就不信了。** 流水表的实现成本远低于并发优化，教学密度（对账思维）却更高——这是典型的「看起来不重要，其实很关键」。

### 洞察 5：注释里承认的债，最容易在关键时刻被忘掉

`OrderTransactions.pay` L75 的注释写着：「真实支付必须移出长事务，并使用支付单/回调幂等。」这句话是对的，但它**没进路线图**。
这是全项目**唯一一处把外部调用包进数据库事务**的地方——现在无害，因为模拟支付零副作用。但它是「接真实支付」那天唯一的阻断项，而它目前只活在一行注释里。
**建议：凡是在注释里写下「真实场景下必须改」的地方，都应当登记进路线图，否则它一定会被忘掉。**

## 附：本分析中「已论证的取舍，**不列为差距**」的项

以下各项常被当成差距，经核对属于**有意识且论证充分的工程取舍**，本文不要求补：

| 项 | 为什么不是差距 |
| -- | -------------- |
| 没接 Kafka / RabbitMQ | Outbox 已覆盖「生产/消费/确认/重试/退避/死信/重启恢复」语义（**唯一失效场景见洞察 1，已单列为 P1-4**） |
| 用 `close_reason` 而不用第四态 `CLOSED` | 已在 `docs/路线图.md` 实测论证：H2 给内联 CHECK 起自动名 `CONSTRAINT_51`，写进迁移跨环境会失配 |
| 关单扫描不照抄 `last_scanned_at` 游标 | 已被处理掉的订单会离开结果集，队列天然收敛，无队尾饥饿（项目决策第 5 条） |
| 提醒不做时间冷却 | 基线价格重置已天然保证「一次降价 = 一条提醒」，冷却是伪需求（已移除） |
| 购物车不做乐观锁版本号 | `MERGE` 已保证同商品累加原子，是伪需求（**已在路线图移除，不复活**） |
| 主动提醒不复用 `outbox_event` | V8 迁移注释已论证：混用会让外键与重试策略同时失真 |
| 站内提醒是「展示型数据」 | 与「必须送达」是两种语义，分开建模是对的 |
