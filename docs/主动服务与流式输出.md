# 主动服务与流式输出

本文记录助手从「会导购」走向「会主动、看得见」的这一期改造。

上一期（[导购闭环与记忆](导购闭环与记忆.md)）解决的是「像不像专业导购」：能不能把东西放进购物袋、
能不能记住用户是谁。这一期解决两个更接近「专业感」的问题：

1. **它等结果时在干什么，用户看不见。** 一次回答动辄十几秒，界面只有一个转圈。
2. **它只在用户开口时才存在。** 真正专业的导购会记住「你说过想要但嫌贵」，然后降价那天回来说一句。

## 一、能力对照

| 能力 | 专业助手/淘宝的做法 | 本期之前 | 本期之后 |
| ---- | ------------------ | -------- | -------- |
| 等待反馈 | 边想边说，「正在为你搜索…」 | ❌ 转圈 → 一次性出结果 | ✅ SSE 逐帧推进度，「正在搜索商品」 |
| 正文呈现 | 一个字一个字地出来 | ❌ 憋十几秒后整段弹出 | ✅ token 级逐字输出，增量过守卫 |
| 记住偏好 | 用户明说时记，推断的也能补上 | ⚠️ 只认模型主动调工具 | ✅ 规则 + 模型双路径，轮后自动抽取 |
| 降价提醒 | 「你关注的商品降价了」 | ❌ 无 | ✅ 关注商品 → 改价即推提醒 |
| 补货提醒 | 「补货了」 | ❌ 无 | ✅ 缺货关注 → 到货即推 |
| 关联推荐 | 「买过 X 的人也在看 Y」 | ❌ 无 | ✅ 共同购买 → 同类目 → 热销三级降级 |
| 不打扰 | 提醒一次就收手 | — | ✅ 提醒后重置基线，同一次降价只说一次 |

## 二、流式输出：让「在干什么」可见

### 为什么是 SSE，不是 WebSocket

进度推送是**单向、短时、随请求生随请求灭**的。WebSocket 要额外维护握手、心跳、连接注册表，
换来的全双工在这里一次都用不上。SSE 本质上就是「一个不会立即结束的 HTTP 响应」，
天然对齐这个场景，也天然继承了现有的登录态与 CSRF 校验——不需要为它另做一套鉴权。

### 为什么前端用 `fetch` 读流，不用 `EventSource`

`EventSource` 只能发 GET、不能带自定义头，于是**既传不了 CSRF 令牌，也传不了消息正文**。
所以前端用 `fetch` + `response.body.getReader()` 手动解析同样格式的 SSE 帧
（`parseSseFrame`）。代价是要自己处理分帧（帧以空行 `\n\n` 结尾，一次 `read()`
可能拿到半帧或多帧），收益是这条通道和普通接口共享完全一样的鉴权方式。

### 进度是旁路，不是链路

进度回调接口 `TurnListener` 只有三个方法，全部带默认空实现：

```java
public interface TurnListener {
    TurnListener NOOP = new TurnListener() {};
    default void onStage(String stage) {}
    default void onToolStart(String toolName, String args) {}
    default void onToolEnd(String toolName, String status, long latencyMs) {}
}
```

关键在于 `AgentLoop` **不关心有没有人在听**：

- 旧的 5 参数 `run(...)` 委托给 `TurnListener.NOOP`，同步端点一行没改；
- 所有回调都包在 `notifySafely(...)` 里，监听器抛异常只记 debug 日志。

这一条不是洁癖。进度是「锦上添花」，而它触发的位置在每一轮工具调用前后——
如果监听器异常能冒泡，那么**一个用户关掉浏览器标签页，就可能让整个轮次失败**。
一个装饰性功能不该有这个权力。

### 一旦返回 `SseEmitter`，错误只能从流里表达

返回 `SseEmitter` 的那一刻 HTTP 200 与响应头就已经发出去了。之后的任何失败
（会话不存在、并发闸门拒绝、模型超时）都**不可能再改成 500**，只能从流里以 `error` 事件收尾。

这不是缺陷，是必须接受的前提。所以事件协议被设计成自带收尾：

| 事件 | 载荷 | 含义 |
| ---- | ---- | ---- |
| `open` | `{conversationId}` | 通道已建立，可以开始期待后续事件 |
| `stage` | `{stage}` | 轮次级阶段：`thinking`（思考中）/ `vision`（正在看用户上传的图片，见「多模态与以图搜款」） |
| `tool` | `{tool, phase, label, status?, latencyMs?}` | 工具开始/结束，`label` 是中文文案 |
| `delta` | `{text}` | 模型产出的一个文本增量。中间轮也可能有——那不是最终答案 |
| `guard` | `{reason}` | 增量被判不安全，已推出的增量作废，等 `done` 带来权威文本 |
| `done` | `SendMessageResponse` | 正常收尾，载荷与同步端点完全一致。**`reply.content` 是权威文本**，可能已被输出守卫改写 |
| `error` | `{code, message}` | 失败收尾，`code` 是业务错误码 |

前端在 `delta` 到达时就逐字渲染，但**只在拿到 `done` 时才定稿**——因为 `done` 里的正文
是服务端过完输出守卫的版本，可能与刚才逐字显示的不一样。拿到 `error` 时按业务错误提示——
两种收尾都算「流正常结束」，所以不会出现「转圈永远转下去」。

### 线程模型：不占 Tomcat 的工作线程

```java
turnExecutor.execute(() -> { ... });   // 助手专用线程池
return emitter;                        // 请求线程立刻归还
```

与同步端的 `Callable` 版本同理：绝不把「等模型」的时间计入 Tomcat 工作线程。
默认 200 个 Tomcat 线程被几十个等待模型的请求吃干净，是一个功能拖垮整个站点的经典路径。

线程池满时（`RejectedExecutionException`）推一个 `ASSISTANT_BUSY` 事件，
而不是静默留下一个空流。

### 工具名 → 中文文案放在服务端

`TurnStreamSink.TOOL_LABELS` 是工具名到「正在搜索商品」的映射。放在服务端的好处是
**新增工具时前端零改动**；代价是没人提醒你补那一行，忘了补不会报错、不会失败任何现有测试，
只会在界面上显示 `recommendRelated` 这样的裸工具名——而且往往到演示时才被看见。

所以配了一条反向守卫（`ToolProgressLabelTest`）：把注册表里**所有**对用户可见的工具拿出来，
逐个要求它有中文文案。新增工具忘了补，构建期直接失败并告诉你少了哪个。

### 逐字输出：把「在说什么」也推出来

进度条解决的是「它在动」，逐字输出解决的是「它已经在说了」。两者不是一回事：
进度条再好看，正文仍然是憋十几秒后一次性弹出。

实现上，`TurnListener` 多了三个方法（默认实现照旧为空）：

```java
default boolean consumesTokens() { return false; }  // 是否要逐字增量
default void onToken(String token) {}                // 一个文本增量
default void onTokensStopped(String reason) {}       // 已推出的增量作废
```

`consumesTokens()` 是一个**开关而不是装饰**：只有真正能把增量送到用户面前的监听器
（SSE 的 `TurnStreamSink`）才返回 true，执行循环据此切换到流式模型客户端。
不给这个信号就走同步调用——同步端点、定时任务、演示模式都不该为用不到的功能多付一次连接。

流式客户端是回调式的（`chat()` 立刻返回，结果在另一个线程上给），执行循环用
`CountDownLatch` 把它拉回同步。**这不是偷懒**：循环本身就是顺序的——拿不到这一步的决定
就无法决定下一步，强改成异步只会让状态机复杂一倍，换不来任何好处。

#### 中间轮的文字不是答案

多轮循环里，模型常常先说一句「我帮你查一下」再发起工具调用。这段增量会被推给用户，
但它不是最终答案。前端的做法是：收到 `tool` 事件时把已显示的文字**降级**成灰色小字，
而不是清空——清空会让界面闪一下，那比留着更像故障；等 `done` 带来的权威文本时再整体替换。

真实容器里观察到的序列印证了这个设计不是多余的：

```
stage, delta×16, tool×4, stage, delta×18, tool×4, stage, delta×50, tool×2, stage, delta×36, done
```

四轮里前三轮都有文字输出，最后一轮才是答案。而且模型在调工具前会用**英文**自言自语
（`"I'll check the user's preferences and se…"`），最终答案仍是中文。
「新一轮开始时清空上一轮的过程文字」这一步是必需的，否则真正的答案会顶着灰字样式一路长到底。

#### 逐字输出与输出守卫的窗口

这是逐字输出带来的**新问题**，之前不存在：用户会先看到内容，守卫随后才对完整文本定案。
「整段说完再定案」在流式下等于把泄密内容先完整显示一遍——窗口就是整段生成的时间。

所以增量也要过守卫：每收到一个增量就把它并入缓冲区，用 `OutputGuard.wouldFlag`
检查**已累积的文本**。一旦命中：

1. 立刻停止推送后续增量；
2. 推 `guard` 事件，前端清掉已经显示的字；
3. 让这次响应正常走完，由上层对**完整文本**过守卫并整段替换——那才是唯一权威的定案。

缓冲区扫描是 O(n²)（n 是本轮已收到的字符数，上限即模型最大输出），在 2000 字量级上
可以忽略；换来的是「泄密内容一到就停」。

窗口并没有被消除，只是被压到最小。这是流式输出与输出守卫之间**固有的**张力，
不是实现缺陷，所以写在这里而不是藏起来。

#### 一个编码上的坑

`text/event-stream` 不带 charset 参数，而 HTTP 规范里 `text/*` 默认 ISO-8859-1。
浏览器按 SSE 规范一律按 UTF-8 解析，所以线上没问题；但 MockMvc 会按 ISO-8859-1 解码，
于是测试里任何中文都变成乱码——那是测试工具的推断，不是线上真实字节。

正确做法是**直接按 UTF-8 解原始字节**来断言：

```java
String body = new String(result.getResponse().getContentAsByteArray(), StandardCharsets.UTF_8);
```

试图靠在 `produces` 里补 `;charset=UTF-8` 来「修」它是错的——实测那样反而会让写出的
字节被按 latin-1 编码（`好的` 变成 `?????????`）。**先测，再改，别拿推测当结论。**

### 降级

前端 `streamTurn` 在**非 200** 或**拿不到 `response.body`** 时自动回退到原非流式端点，
同步端点也一直保留（有测试断言其仍可用）。流式是体验增强，不该成为新的单点。

## 三、轮后自动抽取偏好：把「记住」从自觉变成职责

原来记忆只在模型主动调 `rememberPreference` 时才写入。这依赖模型每一轮都记得住这件事——
而模型在忙着搜商品的时候，很容易把「顺手记一下」忘掉。

本期改成**轮后自动抽取**，两条路径并行：

| 路径 | 成本 | 开关 | 认得什么 |
| ---- | ---- | ---- | -------- |
| 规则 | 零 | 永远开启，不可关 | 高精度句式：「预算 200 以内」「送给妈妈」「不要红色」 |
| 模型 | 一次额外调用 | `mall.assistant.memory.auto-extract-model` | 规则覆盖不到的表述 |

规则路径只认**高精度句式**，宁可漏、不可错。抽取器是纯函数（`fromRules`），
因此可以直接单测，不需要起 Spring 上下文。

### 为什么两条路径都收敛到 `MemoryWriter`

如果把校验复制一份到自动抽取里，两条路径迟早会分叉——而分叉出来的那条
就是**静默绕过守卫的通道**。所以 `MemoryWriter` 是记忆的唯一写入路径：

```
MemoryTools（模型主动写）─┐
                          ├─→ MemoryWriter ─→ 键白名单 → 长度截断 → 输入守卫 → 入库
PreferenceAutoExtractor ─┘
```

### `source`：自动抽取只增补，不改写用户的原话

新增 `source` 字段区分两个来源（`MODEL` / `AUTO`），并配一条覆盖规则：

- **AUTO 永不覆盖 MODEL**。用户明确说过「预算 200 以内」，系统推断出的「预算 150 左右」
  只能另立一条或放弃，不能把用户亲口说的话改掉。用户看到自己的话被系统悄悄改过，信任就没了；
- 同源可以自我更新（推断可以被更好的推断取代）；
- 置信度与 TTL 也不同：`AUTO` 置信度 0.55、45 天过期，`MODEL` 是 0.80 与 90 天。
  推断的偏好本来就比明说的更可能过时；
- 前端对 `AUTO` 条目显示「助手推断」标记，用户能分辨哪些是自己说的、哪些是猜的。

### 不能拖慢、也不能搞坏主回答

自动抽取跑在独立单线程池（`assistant-memory-extract`）上，队列有界（64），
满了就丢弃并计数。任何失败只记 debug 日志——**用户要的是回答，不是「系统正在学习你的偏好」的报错**。

模型路径还有冷却时间（`auto-extract-cooldown-seconds: 60`），避免连续多轮重复调用。

### 测试 profile 里默认关闭

`auto-extract` 在 `application-test.yml` 里是关的，由 `PreferenceAutoExtractTest` 显式打开。
原因很实际：异步写库会让「记忆有几条」这类计数断言随执行时序飘，
一个偶尔红的测试比没有测试更糟。

## 四、主动服务：提醒与关联推荐

两个概念，两张表：

| 概念 | 表 | 语义 |
| ---- | -- | ---- |
| 关注 | `mall_product_watch` | 我在盯这件商品。带**基线价格**与**关注时的库存状态** |
| 提醒 | `mall_alert` | 系统对我说过一句话。带已读状态 |

基线价格是关键设计：**有基线才知道什么叫「降价」**。没有基线的「关注」只能做「变价提醒」，
而变价里一半是涨价——那不是帮忙，那是骚扰。

### 提醒一次就重新武装

降价提醒发出去之后，把 `baseline_price` 重置为**当时**的现价；补货提醒发出后同样更新库存状态。
于是：

- 同一轮降价只提醒一次（`rearmPrice` 之后现价 == 基线，不再满足「更低」）；
- 想再收到提醒，就得再降一次；
- 涨价不提醒（不是「更低」）。

「提醒一次就收手」是主动服务的生死线。会重复轰炸的功能会被用户关掉，
而「关掉之后再也不提醒」等于没做这个功能。

### 事件驱动 + 定时兜底，两条都要

```
店员改价 ──→ ProductChangedEvent ──→ @TransactionalEventListener(AFTER_COMMIT) ──→ 扫描 ──→ 提醒
                                          │
                                    @Scheduled(fixedDelay) ──→ 扫描 ──→ 提醒
                                          ↑
                          运维直接改库 / 绕过接口的变更，只能靠这条
```

- **事件驱动**保**及时性**：改价的人在等反馈，不能让提醒等下一个五分钟；
- **定时兜底**保**完整性**：绕过接口的直接改库不会发事件，只有周期扫描能捞到。
  这条有专门的测试（`scanCatchesDirectChangesAndRearms`）——测试里刻意绕过接口直接改价，
  验证兜底路径真的有效。

事件用 `AFTER_COMMIT`：价格还没提交就发提醒，会推出「提醒了一个不存在的新价」。
`fallbackExecution = true` 则是为了在没有事务的调用路径下也不静默丢掉事件。

### 扫描本身必须封顶，但封顶不能以牺牲队尾为代价

单次扫描最多处理 `mall.proactive.max-alerts-per-scan`（默认 500）条候选。
一次全量扫描如果处理十万条，第一个挨饿的就是正常请求——定时任务最该防的就是自己。

但这里有一个曾经真实存在过的缺陷值得记下来，因为它完全符合「规模化之前看不出来」的特征。
扫描最初写成这样：

```sql
SELECT ... FROM mall_product_watch w JOIN product p ...
ORDER BY w.created_at, w.product_id LIMIT :limit
```

关注总数 ≤ 500 时它完全正确；一旦超过，**排在最末尾的那批关注永远进不了窗口**——
它们降价了也没人被告知。可怕之处在于它毫无症状：日志照常打出「扫描了 500 条」，
没有任何一处会变红，用户只是慢慢不再信任「降价会提醒我」这件事。

修法不是把 500 调大（那只是推迟问题登场），而是给扫描一个游标：

```sql
WHERE  p.price < w.baseline_price                                  -- 只看真的有变化的人
    OR (w.in_stock_at_watch = FALSE AND p.stock > 0)
ORDER BY COALESCE(w.last_scanned_at, '1970-01-01') ASC, ...        -- 最久没被照顾的优先
LIMIT :limit
```

配套三个决定，各有理由：

- **候选过滤下推到 SQL**。扫描最频繁，它的成本应该由「有多少人真的有话说」决定，
  而不是由「总共多少人点了关注」决定。
- **扫到就推进游标**，哪怕这一条没有发出提醒。若只有「真的发了提醒」才推进，
  那些暂时不需要提醒的行会一直停在队首反复占名额，队尾的人还是轮不到——饥饿换个形式又回来了。
- **返回剩余积压量**并写进日志。`remaining` 持续不为零 = 有一批用户正被系统性跳过，
  这是唯一能让这件事浮出水面的手段。

于是 `max-alerts-per-scan` 不再是「能服务多少人」的上限，而退化成它本来的含义：**一次处理多少条**。

> 这里也记下一个**刻意没做**的东西：提醒的时间冷却（比如「同一件商品 6 小时内只提醒一次」）。
> 结论是不需要——基线机制已经承担了重复抑制：提醒后基线被重置为当时的现价，
> 所以 100→95 提醒一次之后，价格回涨到 100 再跌到 96 **不会再触发**，只有真的跌破 95 才会发第二条。
> 时间冷却要解决的抖动刷屏，基线已经解决了；再加一层只会把「再跌一次再提醒一次」
> 这条真实有用的语义一起吞掉。加东西之前先确认它要解决的问题是不是已经被解决了。

### 关联推荐：三级降级，每条都必须有理由

```
共同购买（准）─→ 同类目补充（广）─→ 热销兜底（不空手而归）
```

种子来自**购物袋 + 最近 20 笔已支付订单**（最多 12 个）。共同购买是 `order_item` 的自连接统计。

两级降级的原因不同：同类目解决「共同购买数据太稀疏」（新商品永远没有共同购买记录），
热销解决「新用户没有种子」。推荐系统的降级是常态，不是例外。

**每条推荐必须带 `reason`。** 没有理由的推荐看起来像广告位，有理由的推荐看起来像帮忙——
这个字段是「导购」和「货架」的分界线。措辞上也刻意避开「关注」二字，
因为「关注商品」在本期已经是一个专有功能（降价/补货提醒），同词不同义会让人
误以为推荐看了关注列表。

### 第四类提醒：订单超时关闭后的弃单召回

关注提醒之外，主动服务还接了一个触发源：**订单因超时被自动关闭**时，提醒用户「东西还在」。
它同样遵守这里的两条规矩——只在该打扰的时候打扰（**主动取消的订单不召回**，
人家是不想买了），以及每条推荐都必须带理由。

细节见 [订单超时与弃单挽回](订单超时与弃单挽回.md)（含「为什么必须在事务提交后才召回」）。

### 关注是私密的

接口的作用域是 `Principal`，不是请求参数——「查看/修改别人的关注」在接口层面
就没有表达方式。提醒同理。这两条都有测试（`alertsAreScopedToOwner`，以及冒烟里的跨账号检查）。

### 助手与页面共用同一份数据

助手的 `watchProduct` / `myWatches` / `myAlerts` / `recommendRelated` 走的是同一套 Service。
所以「助手帮你关注」和「你自己点关注」是同一份数据——不会出现「我跟助手说了，但页面上没有」。

系统提示里也写清了一条边界：

> 你没有任何能力自己制造提醒、改价或改库存。

助手能做的只是「设置关注」，提醒由真实的商品变更驱动。这句话是给模型的护栏，
防止它为了让用户满意而虚构一个「已经帮你盯着了，降价就通知你」的承诺之外的即时效果。

### 店员改价接口：不只是运营工具，也是触发源

`POST /api/products/{id}/price` 与 `/stock` 仅店员可用（`SecurityConfig` 的 URL 级限制
加上方法级校验，形成双重防线）。它们的存在让主动服务的演示路径完整：

```
店员改价 → 关注的人当场收到提醒
```

一处「用户在等降价提醒」的价值，只有在价格真的会变时才成立。

## 五、关键取舍

| 取舍 | 选择 | 理由 |
| ---- | ---- | ---- |
| 推送协议 | SSE 而非 WebSocket | 单向短时场景，且天然继承登录态与 CSRF |
| 前端读流 | `fetch` 读流而非 `EventSource` | 需要带 CSRF 令牌与请求正文 |
| 进度失败 | 一律吞掉 | 装饰性功能不该有能力让轮次失败 |
| 记忆写入 | 单一写入路径 | 复制校验会分叉出静默绕过通道 |
| 自动抽取 | AUTO 不覆盖 MODEL | 推断可以补，不能篡改用户原话 |
| 提醒策略 | 提醒后重置基线 | 不打扰是主动服务能存在的前提 |
| 触发方式 | 事件 + 定时双触发 | 分别对应及时性与完整性，缺一不可 |
| 推荐理由 | 必填 | 分界「导购」与「广告位」 |
| 提醒存储 | 新建表而非复用 `outbox_event` | 投递语义与重试策略完全不同，复用比新建更贵 |

关于最后一条值得展开：`outbox_event` 的 `aggregate_id` 外键指向 `mall_order(id)`，
且它承载的是「必须送达、失败要重试、重试有上限」的投递语义。
站内提醒是「读一次就没了」的展示型数据，两者混用会让外键和重试策略同时失真。

真实容器冒烟（`tests/async-smoke.cjs`）本期扩到 18 组断言，覆盖 MockMvc 证明不了的部分：

- **流式逐帧推进度**：真实 Tomcat 上一次 `200` 的响应里观察到
  `open,stage,tool×4,stage,tool×4,stage,tool×2,done`，且进度事件全部早于 `done`；
- **逐字输出**：同一次响应里收到 125 个 `delta` 增量（240 字），真实序列为
  `stage,delta×16,tool×4,stage,delta×18,tool×4,stage,delta×50,tool×2,stage,delta×36,done`；
  拼接后的增量以最终正文结尾（逐字内容与落库内容没有分叉），最终正文为中文；
- **流式端点的安全性与同步一致**：注入消息在流式通道上同样被拦下，回复里不含系统提示；
- **事件驱动的完整业务链**：关注 → 店员降价 → 当场收到 `PRICE_DROP`（**不调用 scan**）→ 涨价不提醒 →
  退订后列表为空；
- **同一次降价不重复提醒**；
- **跨账号隔离**：关注列表、提醒都不属于别人；
- **权限**：未登录读关注 `401`、普通用户改价 `403`；
- **关联推荐**：非空、每条带理由、不把购物袋里已有的商品又推荐一遍；
- **原价还原**：脚本在 `finally` 里把改过的价格还原，冒烟不给本地库留副作用。

## 七、已知局限与下一步

- 提醒只有站内一种通道。邮件/短信需要外发凭据与退订机制，属于另一类问题（也涉及合规）。
- 关联推荐用的是「共同购买」的简单共现计数，没有做协同过滤，也没有排除已购商品之外的负反馈信号。
- 定时扫描是全表按 `id` 顺序扫，规模上来后要改成分片或增量（当前有 500 条/次的封顶）。
- **逐字输出与输出守卫之间仍有窗口**：泄密内容在被判定前会先显示一小段时间
  （已压到「一个增量」的量级，但无法消除——这是流式固有的，不是实现缺陷）。
- 中间轮的模型自言自语（含英文）会被推给用户，目前只做了视觉降级，没有做「是否展示思考过程」的开关。
- 以图搜款（多模态输入）**已落地**，见 [多模态与以图搜款](多模态与以图搜款.md)。
