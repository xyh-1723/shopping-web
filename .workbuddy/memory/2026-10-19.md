## 我在核验中追加发现的两件事（比 t27 报告的更深一层）

1. **F3 的根因不是「结果太长」，是排序本身。** `CatalogTools.searchProducts` 排序是
   `Comparator.comparing(price)`（价格升序）且无 limit。模型想知道「你们有什么」而调用
   `searchProducts("","",null)` 时，返回的是**全店最便宜的一批** —— 6 件时无所谓，
   500 件下这等于助手永远只会推荐廉价货。**加 limit 只治长度，不治排序。**

2. **t27 漏了 `StaffTools.inventoryAlerts`**（店员低库存告警）同样无 limit：
   500 件下若有大量低库存商品会一口气吐几百件，然后被 harness 裁到 4000 字符，工具直接失效。

## 硬教训（本轮新增，可复用）

### 1. flake 类缺陷的验收标准必须「能区分修与不修」，重复连跑无效

我给 t26 定的验收标准是「连跑 10 次必须 10 次全绿」。
工程师证明：**单类连跑 30 次根本复现不出来** —— 那就不修也是全绿、修了也是全绿，
**这个标准区分不了修与不修，是自欺欺人**。

改为：
- **主证据**：拉宽窗口的探针 —— 修复前必须稳定红、修复后必须稳定绿。
- **回归**：10 次连跑仍然跑，但只用于确认没引入新的不稳定，**不作为修复有效的证据**。

推广：**任何验收标准都要先自问「它能不能区分做与不做」**。不能区分的标准，跑了也是白跑。

### 2. 改硬编码数量的断言，不许换成一个新的数字

商品从 6 件扩到 506 件后，`MallIntegrationTest` 与 `tests/browser-smoke.cjs` 里
硬编码「6 件」的断言会红。把 `isEqualTo(6)` 改成 `isEqualTo(506)`，
**等于把「6 件」这个脆弱前提换成「506 件」这个同样脆弱的前提** ——
下次数量再变又红，而且红得毫无信息量。

按优先级改：
1. **改成不依赖总数的性质断言**（「列表里能找到 1 号马克杯」「筛选结果全部 category==文具」）
2. 从数据库动态取真实数量再断言（「列表件数 == product 表 count」）
3. 最后才硬编码，且只在断言语义真的是「目录规模」时才用（`isGreaterThan(500)` 有意义）

### 3. 我自己的误判：看到文件不等于看到「同一个人在做」

我看到 t26 工作树里有 `DeferredTurnExecutor.java` / `StreamStressProbeTest.java` / `StreamRaceProbeTest.java`，
就判断「工程师正在做探针，进展良好」。实际上工程师报告「有另一个 agent 在撞车」。
查 runtime.json 才发现：**running 的只有 4 个，且分别在 4 棵不同工作树** ——
那些文件是上一个会话遗留的已终止 agent 的产物（时间戳 17:42/17:54 早于本轮产出）。

**教训：判断「谁在干什么」要查 runtime.json + 文件时间戳，不能只看文件存在。**
（此前记忆里已记过「派工报 name already in use ≠ 没启动」，这是同一类问题的另一面：
反过来「文件存在」也不等于「对方正在写」。）

### 4. 约束缺口：库允许 0 元商品，业务不允许

`V1` 的 CHECK 是 `price >= 0`，但 `ProductController.PriceRequest` 改价接口是 `@DecimalMin("0.01")` ——
**商品不可能被改成 0 元，却可以被直接插成 0 元**。与 V18 补 reason_code CHECK 同类。
已让 t29a 查有无测试依赖 0 元商品，无依赖则补 `ck_product_price_positive CHECK (price > 0)`（**显式命名**）。

### 5. illustration 只有 6 个合法值

`src/main/resources/static/art/` 下只有 bag/cup/hero/keyboard/lamp/notebook/timer 七个 svg，

`cup / notebook / lamp / bag / keyboard / timer`。前端渲染 `/art/{x}.svg`，填错就是 404 破图。
