## 下午追加：订单/退款架构摸底（回答「有没有 MQ、退款可追溯吗、Redis 怎么同步」）

### 结论一：项目没有 MQ，也没有 Redis（两个都要先纠正提问前提）
- `pom.xml` 无 amqp / kafka / rocketmq 依赖；`messaging` 包不是 MQ，是
  **本地 outbox 表 + `@Scheduled` 轮询**（`OutboxDispatcher` → `MessageWorker` → `MessageProcessor`）。
- **Redis 只出现在注释里**（`AssistantConcurrencyGate` 说"生产环境可换 Caffeine/Redis"）。
  所有 `ConcurrentHashMap` 都是限流/指标/调度去重，**没有任何业务数据进内存缓存**，
  所以「Redis 与 DB 同步」这个问题当前不存在——也就不存在这个一致性风险面。

### 结论二：退款链路可追溯，四张表串得起一条链
`refund`(状态机+审批人+分流结果) → `wallet_ledger`(REFUND 入账,actor=放款责任人)
→ `stock_ledger`(reason=REFUND) → `outbox_event`/`notification_delivery`(通知留痕)。
关键点：`events.publish` 是 `Propagation.MANDATORY`，**通知行与退款状态在同一事务提交**，
不存在"退款成功但没通知"。

### 结论三（实测确认的缺陷）：一笔订单只能真正放款一次
- 服务层 `requireWithinRemaining`(累计已退+本次<=实付) 与 `hasInFlight`(只挡在途)
  **都预期支持多笔部分退款**；
- 数据层 V16 `uq_wallet_ledger_order_reason(order_id, reason)` **只允许一笔**。
- 实测：第一笔 ¥20 成功 → 第二笔 ¥10 抛 `DuplicateKeyException`（500，非友好 409）。
- 好消息：**整笔事务回滚**，refund 行不留、余额不动、对账为 0，没有半吊子。
- V16 注释已写明这个耦合点（"放开部分退款须换成 refund.id 粒度"），但 V17 未同步改。
- 已固化成 `PartialRefundLimitTest`（绿），将来放开多笔时应**替换**而非改断言。

### 结论四：追溯性的小缺口
`outbox_event.aggregate_id` 与 `notification_delivery.order_id` 都只到**订单**粒度，
没有 `refund_id` 列。一笔订单多笔退款场景下，"这条 ORDER_REFUNDED 通知对应哪笔 refund"
只能靠 order_id + 时间推断。加列需新迁移（V1/V17 已落盘）。
另：`outbox_event.aggregate_id` 有 `REFERENCES mall_order(id)` 外键，而 `refund` 刻意不加
——删订单时两者的约束强度不一致（测试清理顺序已按此写死）。

## 换主库到 MySQL 8.0.31 + 超时关单分片扫描（本轮完成）

### 决定
- **主库从 H2 文件库换成 MySQL 8.0.31**（本地已装，root/123456，口令放 `.db.key`，`*.key` 已被 .gitignore 忽略）。
- **测试仍跑 H2，但必须开 `MODE=MySQL`**；测试自建连接的 URL 统一走 `TestH2.inMemory()/file()`，不许再手拼。

### 踩过的坑（都是真刀真枪炸出来的，别再踩）
1. **H2 不接受 `ts + INTERVAL 15 MINUTE`**（MySQL 可以）。日期加减的唯一交集是
   `TIMESTAMPADD(unit, n, ts)`（DAY/HOUR/MINUTE 实测两边都成立）。`DATEADD` 只 H2 有，`DATE_ADD` 只 MySQL 有。
2. **`MODIFY COLUMN` 与 `ALTER COLUMN ... SET DATA TYPE` 没有交集** —— 靠 H2 `MODE=MySQL` 解决，不要去找交集。
3. **`DATABASE_TO_LOWER=TRUE` 会让 H2 把标识符存成小写**，于是报错里的索引名变 `uq_xxx`，
   一批断言 `UQ_WALLET_LEDGER_ORDER_REASON` 的测试全红。**只加 `MODE=MySQL`，不加 TO_LOWER**。
4. **`driver-class-name: com.mysql.cj.jdbc.Driver` 会顶掉测试里 H2 的 URL**（报 claims to not accept jdbcUrl）。
   不写驱动类名，让 Spring Boot 按 URL 推断。
5. **`characterEncoding=utf8mb4` 对 Connector/J 是非法值**（Java 没有这个字符集名），应用直接连不上库。别写。
6. **Flyway 10+ 把各库支持拆成独立模块**：只有 `flyway-core` 连 MySQL 会抛
   `Unsupported Database: MySQL 8.0`。必须加 `flyway-mysql`（版本与 core 一致，由 parent 托管）。
7. 改过历史迁移脚本 → **Flyway 校验和失效**，本地库必须重建（不允许改已应用的迁移）。
8. `surefire:test` 单独跑不会重新拷贝资源，读的是旧 `target/classes`；排错时用完整 `mvn test`。
9. `target/surefire-reports` 里的**旧报告会诈尸**（源文件删了，XML 还在），全量前先把目录移走再看结果。

- 前端：`app.js` 改为服务端分页（PAGE_SIZE=24）+ 250ms 搜索防抖 + `#pager`；
  **新增 `knownProducts` 跨页缓存**——分页后购物袋里的商品可能不在当前页，
  登录用户改从 `cartView.items`（服务端已带 name/illustration/stock）取，不再依赖 `products` 数组。
- **LIKE 通配符转义**与**低库存 total 不被 limit 截断**是两条必须单独守的性质。

### 阶段 2：扩容到 5k 常驻 + 50k/500k 压测
- `V23__catalog_scale_5k.sql`：新增 4,494 件（id 507..5000），总 5,000 件。
  **生成式 SQL，不是硬编码**（V20 的 500 件是 82KB INSERT，照抄会是 700KB）。
- 名字 = 修饰词(k mod 20) × 品类词(k mod 7) × 规格(k mod 11)，LCM=1540 > 每类 1498，**同分类零重名**。
- **关键方言坑（实测，别猜）**：
  1. `WITH ... INSERT`（CTE 在前）**两边都报语法错**；必须 `INSERT INTO ... WITH RECURSIVE ... SELECT`。
  2. **MySQL `cte_max_recursion_depth` 默认只有 1000**。递归到 4494 会直接失败。
     解法：只递归到 10 造 0..9，再用**数位笛卡尔积**拼 0..1997 —— 递归深度与要造多少件无关。
  3. 避免 `FLOOR`/`CAST` 造成的 DECIMAL 与 INT 隐式转换差异：全程整数 + `MOD`。
  4. `ANALYZE TABLE product` 在 H2 MODE=MySQL 下也能跑通（已验证）。
- 数据核对（真 MySQL 8.0.31）：5,000 件 / id 1..5000 **零缺号** / 同分类**零重名** /
  分类 1666·1667·1667 / 插图 6 种齐全 / 售罄 45 件、低库存 405 件。

### ⚠️ 500k 下的两个新瓶颈（已知，未修）
1. **`SELECT COUNT(*)` 全表计数**：500k 时首页 HTTP 449ms，其中大头是 count。
   淘宝做法是给"约 N 件"或缓存总数，不追求精确 total。
2. **深翻页 OFFSET**：500k 时第 1000 页 72ms、末页 2.1s —— OFFSET 要扫过前面所有行。
   淘宝做法是**禁深翻页 + 游标分页**（`WHERE id > :lastId`）。
   ⇒ 5k 常驻档下两者都无感（10ms），只在 50k/500k 压测档才显现。

## 阶段 3a 完成：商家地基 + 归属 + 隔离（实测数字）

### 起因（一句话）
加 `merchant` 表之前，全系统**只有一个** `merchant` 账号，退款审批只判角色不判归属。
在这种地基上造 N 个商家账号 = N 个都能看/批全部退款的账号 = **成倍的越权，不是扩容**。
所以先落归属维度，再谈数量。

### V24__merchant_foundation.sql
- 新表 `merchant(id, code, name, owner_username UNIQUE, status)`。
  **`owner_username` 是「账号 → 店」的唯一绑定点**（一个账号只开一家店）。
- `product.merchant_id NOT NULL`（无默认值）→ 5000 件分给 200 家，每家恰好 25 件。
- `order_item.merchant_id NOT NULL`（无默认值）→ **下单那一刻从商品拷贝**，
  商品以后改挂别的店，历史订单的归属不漂移（这是「为什么不每次 JOIN product 现查」的理由）。
- 1 号店的 `owner_username` 刻意沿用既有 `merchant` 账号 → 既有契约与测试不漂。

### 方言实测（tools/MerchantDdlProbe，H2 2.3.232 + MySQL 8.0.31 各跑一遍）
| 写法 | H2 | MySQL 8.0.31 |
|---|---|---|
| `INSERT ... WITH RECURSIVE ... SELECT`（数位笛卡尔积） | ✔ | ✔ |
| `CAST(x AS VARCHAR(n))` | ✔ | **✘ 语法错**（只认 `CHAR`）→ 全程改用 `CONCAT` 转字符串 |
| `ADD COLUMN ... NOT NULL DEFAULT 1` | ✔ | ✔ |
| `ALTER COLUMN ... DROP DEFAULT` | ✔ | ✔ ← **给大表加非空列的可移植写法** |
| `ALTER COLUMN ... SET NOT NULL` | ✔ | **✘**（MySQL 要 `MODIFY COLUMN`） |
| `UPDATE t a SET a.c = (SELECT ...)` 关联子查询回填 | ✔ | ✔ |

**口诀**：加非空列 = `ADD ... NOT NULL DEFAULT n` → 回填 → `DROP DEFAULT`。
最后一步不能省：留着 DEFAULT = 以后忘写 `merchant_id` 也能插进去、静默落到 1 号店。

### 账号怎么来的
**不再手写**：`SecurityConfig` 从 `merchant` 表生成，一家店一个账号（角色 `USER,MERCHANT`）。
同一份口令只做**一次** BCrypt、复用哈希串（BCrypt cost=10 一次 60-100ms，200 次会把启动拖到 20 秒）。

### 隔离落点
- `RefundRepository.pendingQueueOf(merchantId, limit)`：用 `EXISTS(order_item.merchant_id)`
  而不是 `JOIN`（JOIN 会把同一笔退款按明细行数重复 N 遍）。
- `RefundService.approve/reject`：角色之外再判 `involvesMerchant(orderId, shopId)`，
  不属于自己店 → 404（与「订单不是你的」同一个口径，不泄露存在性）。
- `OrderRefunds.pendingQueue(int)` → **`pendingQueueFor(String viewer, int)`**：
  可见范围由账号推导（店员全站 / 商家自己店 / 都不是 403），
  **刻意不接受「要不要过滤」的开关**——那个 boolean 迟早会在新入口传错。

### 已知边界（3b 之前）
一笔跨店订单在当下仍是**一个订单、一笔退款**，所以涉及的每家店都能看到并批准它，
且批准退的是整单金额。这是「退款挂在订单上」的直接后果，
修法是 3b 把退款挂到**子订单**上，不是在这里按金额再切一刀（那会长出「退款/部分退款」两套语义）。

### 真 MySQL 核对（tools/MerchantScaleCheck，重放全部 24 个迁移）
商家 200 / 重名店铺 0 / 店主重复 0 / 商品 5000 / 无归属 0 / 越界 0 /
每店 SKU **min=25 max=25** / 有货店铺 200 / 1 号店跨 3 个品类。
隔离查询执行计划：`refund` 走 `idx_refund_queue`（rows=1），`order_item` 走 PRIMARY + FirstMatch，**无全表扫**。
`tools/ApplyToMainDb` 已把 V24 应用到应用真正在用的 `mall` 库（不删库）。

### 测试与变异验证
新增 `MerchantOwnershipTest` 6 条（店/商品/账号、明细归属不漂移、队列按店收窄、
批不动别家店 + 钱没动、驳回也判归属、买家 403）。
**变异验证（注回 → 变红 → 还原）**：
1. 摘掉 `approve` 里的 `requireOwnShop` → `approvingAnotherShopsRefundChangesNothing` 红；
2. 去掉 `pendingQueueOf` 的 `EXISTS` 条件 → `pendingQueueIsScopedToTheMerchantsOwnShop` 红。

### 踩到的坑（这一次的两条）
1. **NOT NULL 无默认值会逼着所有造商品的地方回答「谁的货」**——
   4 个测试夹具（CatalogPaging / CatalogToolsScaleLimit / HttpCompression / StaffToolsInventoryAlert）
   的裸 `INSERT INTO product` 全部挂了 `NULL not allowed for column "MERCHANT_ID"`。
   这是**期望行为**，不是 bug：夹具一律补 `merchant_id, 1` + 注释说明与归属无关。
2. **`MerchantToolsTest` 用 5 号商品（机械键盘 ¥199×2 → ¥373 必进人工队列），
   而 5 号商品归 149 号店**，于是 `merchant` 账号批不动它。
   修法不是把商品挪到 1 号店（会破坏「每店 25 件」，让别的用例随执行顺序变红），
   而是**按商品回查店主账号**（`shopOwner`），越权那几条仍用固定 `merchant`。
