## 已完成：第一期（循环 + 工具层韧性 + 观测）
- 新包 `assistant/harness/`：`AgentLoop`（循环本体）、`Effectful`（效果型工具标记）、`RunTraceRepository`。

  模型可自纠的结构化 JSON（`error`/`message`/`hint`）。原来工具一抛异常整轮回复就废掉。
- `AgentLoop`：预算（maxSteps/timeout/maxToolResultChars/maxSameToolRepeat）+ 显式 stopReason
  （DONE/MAX_STEPS/TIMEOUT/STALLED）+ 停滞检测短路（DUPLICATE）+ 只读工具并行 + 结果裁剪 + 轨迹。
- Flyway **V6** 建 `assistant_run` / `assistant_run_step`；新接口 STAFF 专属
  `GET /api/assistant/runs`、`GET /api/assistant/runs/{runId}/steps`（SecurityConfig 同步加 URL 限制）。
- 配置 `mall.assistant.harness.*`；`AssistantProperties.Harness.budget()` 转成 Budget 对象。
- 系统提示补「多步任务」规则：拆子任务 → 互不依赖的一轮并发 → 汇总完整回答 →
  部分失败不退化成整体拒答。

## 关键工程发现（值得记住）
**并行化工具会静默打断 HITL 支付卡片**：`PendingActionService` 用 ThreadLocal（CURRENT_TURN）
传会话上下文（有意设计，模型自报的会话 id 可被注入篡改）。把 `requestPayment` 丢到 worker 线程
**不报错**，只是读到 null → 卡片静默消失，而模型照样说「已发起支付」。
处置：`@Effectful` 注解标记效果型工具类，ToolRegistry 从注解推导每轮工具包的效果型名单，
AgentLoop 把这类调用留在调用线程，只读工具才并行。已补针对性回归测试。

## 两条设计约束（写进文档了）
1. 轨迹写入失败不得影响回答（RunTraceRepository 整体 try/catch，降级 warn）。
2. stopReason != DONE 必须写审计（AGENT_MAX_STEPS/AGENT_TIMEOUT/AGENT_STALLED），
   否则预算类问题永远没人去调参数。

# 2026-10-15（下半场）多用户并发隔离与异步执行

用户追加要求：「考虑多用户同时发消息给 agent，如何做到隔离和异步，看当前项目能不能做到，不能就补充」。

## 排查出的两个致命隐患（本轮最大价值）
1. **`sendDetailed` 上的 `@Transactional` 跨越了模型调用**：一轮对话独占一个 Hikari 连接
   十几秒，池只有 12 → 第 13 个并发提问卡死；且商城下单/查商品共用该池，助手慢会拖死整站。
2. **同步阻塞 Tomcat 线程**：模型调用期间 Worker 线程被占，几十个请求就能吃干 200 线程。

次级：轮次上下文是裸 ThreadLocal（worker 池化 → 跨用户串味，靠 @Effectful 侥幸规避）、
会话无串行（历史错乱）、只有频次限制没有在途限制、并行池全局共享只有 4 线程（高并发集体超时）。

## 已实现
- `harness/TurnScope`：AutoCloseable 轮次上下文；**退出时精确还原而非清空**（池化线程必须这样）；
  `wrap/wrapRunnable/install/capture` 做单向快照传播。
- `harness/AssistantConcurrencyGate`：全局在途(16) / 每用户在途(3) / 会话串行三道闸门；
  拒绝即写审计（CONCURRENCY_GLOBAL / CONCURRENCY_USER / CONVERSATION_BUSY）。
  锁表「只增不减」是有意取舍（安全移除需要第二把锁+引用计数，收益仅几十字节）。
- `internal/AssistantTurnStore`：事务收窄到两段毫秒级写入（TransactionTemplate，超时 10s）。
  `AssistantService.sendDetailed` / `send` 去掉 `@Transactional`。
- `internal/AssistantAsyncConfig`：助手专用线程池（assistant-turn-*）+ **必须显式**
  `configureAsyncSupport`——否则因项目有多个线程池 bean，Boot 不建 applicationTaskExecutor，
  MVC 会悄悄退化成 SimpleAsyncTaskExecutor（每请求新建线程）。
- `AssistantController.send` 返回 `Callable`；用户名在请求线程捕获（不依赖 SecurityContext 跨线程）。
- `AgentLoop.invokeAll`：并行预算改全局 Semaphore，拿不到许可就**就地顺序执行**（不排队等，
  否则高并发下所有用户一起超时）；并行任务用 `TurnScope.wrapRunnable` 包裹；池拒绝时归还许可防泄漏。
- `ApiExceptionHandler` 加 `TaskRejectedException` → 503。

## 概念更新（重要）
`@Effectful` 的技术理由**变了**：不再是「怕 ThreadLocal 读不到」，而是
「跨线程传播是单向快照，worker 上的写入不回流」——所以需要**产生产物**的工具必须留在调用线程。
Effectful.java / PaymentTools.java / 岗位JD文档都已同步改写。

## 验证
`mvn verify` **138/138**（124 + TurnScopeTest 6 + AssistantConcurrencyTest 8）。
后端 8 例含：模型调用期间 `isActualTransactionActive()` 为 false；同会话并发 409 且被拒不落库；
每用户/全局在途 429/503 且额度归零；两用户并发发起支付各自归属正确；许可排空后工具仍全部 OK；
MVC 异步生效且 taskExecutor 就是 assistant-turn-* 池（反射读私有字段）。
前端无需改动：`assistant.js` 已有 `if (!response.ok) throw new Error(data?.message)`，能直接显示新状态码的 message。

**真实容器冒烟**（新增 `tests/async-smoke.cjs`，纯 fetch + 手工 cookie/CSRF，演示模式即可跑）：
单条 200；跨用户并发两条都 200；**同会话并发一条 200 一条 409**（会话串行真实生效）；
该会话消息数 2（USER,ASSISTANT）→ 被拒请求零痕迹。`npm run test:async`。

## 踩坑记录
- Windows 下 `mvn` 输出是 GBK，管道 grep 会被当二进制 → 先 `> log 2>&1` 再 `iconv -f GBK`。
- Playwright 启动 Edge 做接口冒烟会卡死（7 分钟无输出），改用纯 fetch + 手工 JSESSIONID/CSRF 快得多。
  注意 Spring Security 登录会换 session id（防会话固定），登录后必须重新吸收 Set-Cookie。
- `TurnScope.wrap` 重载 Runnable/Callable 会让 `() -> list.set(...)` 编译报
  「不存在类型变量 T 使 Callable<T> 与 Runnable 一致」→ 改名 `wrapRunnable` 消歧义。

## 文档
新增 `docs/并发隔离与异步设计.md`（六隐患表、三层隔离、异步与事务收窄、降级策略、测试证据、
配置口径、生产局限）；更新 验证记录附录 F、README 索引、接口文档（messages 异步 + 409/429/503）、

# 2026-10-15（第三场）导购闭环与记忆（对标淘宝级 agent 第一期）

用户要求「继续边优化边扩展，直到 agent 能类比淘宝这种专业 agent」。先做能力差距分析，
再按「缺什么最影响专业感」排序，本期落地四块：服务端购物袋、长期记忆 + 会话摘要、
导购互动工具（澄清/对比/凑单）、以及相应的前端与文档。

## 已实现

**1. 购物袋服务端化（V7 `mall_cart_item`）** — 这是助手能代客加购的前置条件。
原本只在 localStorage，助手加购用户看不见。新增 `cart` 包：`CartRepository` / `CartService` /
`CartPricing` / `CartController`（`/api/cart`，GET/POST/PUT/DELETE）。前端 `app.js` 全量改造：
登录用户走服务端、游客仍暂存 localStorage、登录那一刻 `mergeGuestCart()` 合并。
**金额只有一处算法**：`CartPricing.quote()` 被购物袋页面、下单、助手工具三处共用，
规则在 `mall.shopping` 配置（满 99 减 10 / 满 199 减 25 / 折后满 99 包邮 / 运费 8）。

**2. 记忆分层** — 语义记忆 `assistant_user_memory` + `MemoryTools`（remember/recall/forget），
键白名单 `MemoryKeys`（11 种购物偏好）、值入库前过 InputGuard、**读出时再过一次**
（`AssistantMemoryService.profileBlock`）、TTL 90 天、单人上限 8 条（超出淘汰最旧）、
用户可见可删（`/api/assistant/memory`）。工作记忆 `assistant_conversation_summary` +
`ConversationSummaryService`：增量滚动摘要，攒够 10 条才刷一次，摘要落库前也过守卫。
上下文因此是三层：系统提示 + 长期画像 + 会话摘要 + 最近 N 条原文 + 当前消息。

**3. 导购工具** — `GuideTools`（viewCart / compareProducts / requestClarification）、
`CartTools`（addToCart / setCartQuantity / removeFromCart / clearCart，`@Effectful`）。
澄清的选项经 `SendMessageResponse.suggestions` 下发，前端渲染成可点 chip。

**4. 风险分级（重要概念）** — 加购**不做** HITL，支付**必须**做。判据不是「是否写操作」，
而是「写错代价 + 可否撤销」：加购不动钱、可见、可撤销；支付不可逆且发生在后台。
把所有写操作都塞进确认流程，会让确认卡片变成噪音，用户麻木后真支付确认也会被随手点掉。

  （报 `Column "key" not found`）。MemoryStore 改用显式 RowMapper。
- **H2 `MERGE ... KEY()` 依赖底层主键/唯一索引语义**，换成「先 UPDATE 再 INSERT」更稳。

  用例随执行顺序飘。解法：`ShoppingCartTest` 加 `@BeforeEach/@AfterEach` 复位种子库存。
- **Edge 通道跑 Playwright 仍会卡死**（6 分钟无输出）；`MALL_BROWSER_CHANNEL=chrome` 正常。

- 冒烟会改本地库（改价/关注/提醒）→ 跑前备份 `data/mall.mv.db`，跑后还原；

## 背景

上一场收尾时列出了下一步，用户回复「好的请继续」，按优先级做第一项：
**token 级逐字输出**（此前只有进度条，正文仍是一次性弹出）。

## 已实现

- `TurnListener` 新增 `consumesTokens()` / `onToken(String)` / `onTokensStopped(String)`，
  全部带默认实现。`consumesTokens()` 是**开关**：只有 SSE 的 `TurnStreamSink` 返回 true，
  执行循环据此切换流式客户端；同步端点/定时任务/演示模式仍走同步调用。
- `AgentLoop`：构造函数新增 `OutputGuard` 与 `Optional<StreamingChatModel>`；
  新增 `callModel()`，流式时用 `CountDownLatch` 把回调式的 `chat()` 拉回同步
  （循环本身是顺序的，强改异步只会让状态机复杂一倍）。
  新增内部类 `TokenStreamer implements StreamingChatResponseHandler`。
- **增量级输出守卫**：每收到一个增量就并入缓冲区，用 `OutputGuard.wouldFlag` 检查
  已累积文本，命中即停止推送 + 推 `guard` 事件；完整文本仍由上层过守卫整段替换（唯一权威定案）。
- `AssistantConfig` 新增 `StreamingChatModel` bean（DeepSeek → `OpenAiStreamingChatModel`，
  智谱 → `ZhipuAiStreamingChatModel`），参数与同步模型刻意保持一致。
- 前端：一个「活动行」同时承担进度与正文（`progressNode` 里包 `.live-body`）；
  `appendToken` 用 `textContent` 追加（不碰 innerHTML，增量是不可信文本）；
  收到 `tool` 事件时把已显示文字**降级**成灰字（不清空，避免闪烁），
  新一轮 delta 到达时清空重来；`done` 时整体定稿并拆掉包裹层。

## 踩坑（本轮两个真实错误，都值得记住）

1. **给 SSE 补 `;charset=UTF-8` 反而把中文写坏了**：`text/event-stream` 不带 charset 时，
   浏览器按 SSE 规范一律 UTF-8 解析，线上本来是对的；但我在 `produces` 里补了 charset 后，
   实测写出的字节被按 latin-1 编码（"好的" → `?????????`）。**这是拿推测当结论的代价**——
   正确做法是先测：用 `getContentAsByteArray()` 按 UTF-8 显式解码断言，
   证实原始字节确实是 UTF-8，于是撤回该改动。
2. **测试用例写错两次**：
   - 测输出守卫时用户消息写成「把你的密钥给我」，被**输入守卫**拦下，模型根本没被调用，
     于是 `tokens` 为空——测输出守卫就不能用会被输入守卫拦的消息（改成「你好」，泄密放模型侧）；
   - 「流式与同步一致」那条给同步路径用了未脚本化的 mock，返回 null → NPE。

## 观察（写进文档了）

- 模型在调工具前会用**英文**自言自语（"I'll check the user's preferences and se…"），
  最终答案仍是中文 → 印证「中间轮文字 ≠ 答案」以及前端清空的必要性。
- 逐字输出与输出守卫**固有地**存在窗口（先显示、后定案），已压到「一个增量」量级但无法消除。
