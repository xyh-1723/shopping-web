# 2026-10-16（第六场）以图搜款 / 多模态输入

## 背景

上一场收尾时列出的下一步：以图搜款（多模态）> 购物车乐观锁 > 定时扫描分片 >
提醒外发通道 > 「是否展示思考过程」开关。用户回复「好的继续完成」，按优先级做第一项。

## 已实现

**核心设计决策：不在执行循环里传图。**

最直觉的做法是把 `ImageContent` 塞进 `UserMessage` 让 `AgentLoop` 带着跑，我们没有这么做：

- **成本**：循环是「模型 → 工具 → 模型 → 工具…」，图片待在上下文里会**每轮重发一遍**，
  6 轮 = 6 倍开销，而只有第一轮需要它；
- **纯度**：上下文裁剪、历史回灌、轨迹落库全是围绕文本设计的，多模态一进来处处要开特例。
  提前转成文字后**循环一行没改**——这是一期内能安全落地的关键；
- **可审计**：几十个字的描述能复盘，几 MB 的图什么都解释不了。

链路：前端压缩 → `ImageGuard` 四道校验 → `VisionDescriber` 出结构化描述
→ 包进不可信标记作为独立一条 UserMessage → 之后退化成普通文字对话。

**新增文件**
- `assistant/api/ImagePayload`（`mime` + `data`）
- `assistant/vision/UploadedImage`（只活在当次请求内存里，不落库/不写日志/不进轨迹）
- `assistant/vision/ImageGuard`（数量 → 体积 → 声明类型 → **文件头魔数**）
- `assistant/vision/VisualNote`（`available` 两态，unavailable 时携带「如实告知」的指令）
- `assistant/vision/VisionDescriber`（调视觉模型出 JSON，失败一律降级）

  预览与移除，`stage=vision` 显示「正在看图片…」

## 视觉收尾（不配密钥）

**测试隔离陷阱**：视觉密钥留空会回落到同 provider 的对话密钥，而开发环境那份来自
环境变量 `DEEPSEEK_API_KEY`——本机跑会被本机密钥「救活」，CI 上又是另一套结论。
必须在 `@SpringBootTest(properties=...)` 里显式写 `mall.assistant.deepseek.api-key=`。
**换台机器就变结论的测试，比没有测试更危险。**

## 下一项目标：主动服务扫描的完整性（选它的理由）

不是新功能，是现存真缺陷。`watchesToScan` 原为 `ORDER BY created_at, product_id LIMIT :limit`，
关注数一旦超过 `max-alerts-per-scan`，**排在末尾的关注永远进不了扫描窗口**——
降价也不被告知。可怕的是它毫无症状：日志照常写「扫描了 N 条」，没有任何一处变红。

修复（V9 migration）：新增 `last_scanned_at` 游标，按「最久没被扫」升序；
候选条件（降价/补货）下推 SQL；`ScanResult` 新增 `remaining`，积压不为零时日志出 WARN。
于是 `max-alerts-per-scan` 从「能服务多少人」退化成它本来的含义：一次处理多少条。

**关键细节：扫到就推进游标**，哪怕这条没发出提醒。若只有「真发了提醒」才推进，
暂时不需要提醒的行会一直停在队首占名额，队尾还是轮不到——饥饿换个形式又回来。

**刻意没做：提醒时间冷却。** 已论证基线机制承担了重复抑制（提醒后基线重置为当时现价，
100→95 提醒后，回涨 100 再跌到 96 不再触发）。加冷却只会吞掉「再跌一次再提醒一次」
这条已钉住的语义。**加东西之前先确认它要解决的问题是不是已经被解决了。**

## 一条方法论（值得沿用到以后）

新增 3 个测试后做了**反向验证**：把 SQL 临时改回旧写法，三例全部变红
（`Tests run: 3, Failures: 3`），恢复后转绿。**写完就绿的测试不证明任何事情。**

## 整理结果（三处改动）

| 动作 | 项目 | 理由 |
| --- | --- | --- |
| 新增 P0 | 订单超时自动关闭 | 库存被无限期占死，用户天天能感觉到 |
| **移除** | 购物车乐观锁版本号 | **伪需求**：`CartRepository.upsert` 用 `MERGE`，同一商品并发累加本就原子 |
| 搁置 | 视觉模型实测 | 需密钥，用户已明确暂不配置 |
| 重排 | 其余 | 改为按「用户能否感觉到」排序 |

## 订单超时关键设计决策

- **问题本质**：库存下单即预占，`cancel()` 已有释放逻辑 → 缺的不是回退能力，
  而是**时间驱动的触发源**。做法是给已有「关单」动作接第三种触发源，不是新写一套。
- **状态语义**：`status` 保持三态 + 新增 `close_reason`（USER/TIMEOUT），
  而不是加第四态 `CLOSED`。原因有实测依据：
  V1 的 status 是内联 CHECK 约束，H2 自动起名为 `CONSTRAINT_51` 这类形式，
  **写进迁移脚本跨环境会失配**（用 h2 Shell 实测确认）。为一个枚举值美观度担这个风险不值。
  语义区分在展示层做，`close_reason` 本身也能承载将来的风控/客服关闭原因。
- **关单只有一份实现**：超时关闭与主动取消是同一个动作，差异只有 reason。
- **状态变更一律带前置条件**：`UPDATE ... WHERE id=? AND status='PENDING'`，
  影响行数 = 1 才是「我关掉的」，才释放库存 → 幂等来源。
- **支付 vs 超时的竞态**：两边都先 `FOR UPDATE` 拿行锁；输的一方必须给明确文案
  （「已超时关闭，请重新下单」），不能是「未知错误」。
- **扫描不照抄游标**：被处理的订单会离开结果集，队列天然收敛，不需要 `last_scanned_at`。
  **判断依据是「处理之后这行还会不会被再次选中」，不是「上次怎么写的」。**
- **存量回填**：迁移里必须给已有 PENDING 订单补 `expires_at`，否则它们永远关不掉。
- `expires_at` 落库而非 `created_at + 配置算`：配置会改，用户看到的倒计时不能跳变。

## 依赖关系

P0 超时关闭 → P1 弃单挽回（复用已有的提醒 + 关联推荐，只差触发点）。
只做 P0，用户看到的是「订单没了」；接上 P1 才变成「订单没了，东西还在」。

# 第七场：订单超时自动关闭 + 弃单挽回（已实现并验证）

对应提交内容：`V10__order_expiry.sql`、`V11__alert_source_key.sql`、
`OrderProperties/OrderConfig(Clock Bean)`、`OrderExpiryService/Scheduler`、
`AbandonedOrderService/Listener`、`OrderAbandonedEvent`、前端倒计时、
`OrderExpiryTest`(16) + `OrderAbandonedRecoveryTest`(7)、`tests/order-expiry-smoke.cjs`、
`docs/订单超时与弃单挽回.md`。

## 落地时的关键决策（与上一节的方案一致，外加两条实证）

- **先条件更新状态、再归还库存**：`markClosed` 影响 1 行 = 我拿到状态转换权 = 归还库存是我的责任；
  0 行说明别人处理过，安静跳过。顺序反过来会存在「还了库存但订单没关」的窗口。
- **时间做成可注入的 `Clock` Bean**（`OrderConfig`）：否则测「到期前一秒不关、过了就关」
  要么 sleep 15 分钟，要么改库里的 expires_at（变成测 SQL）。
- **弃单召回用 `@TransactionalEventListener(AFTER_COMMIT)`**：事务内被唤醒会读到归还前的旧库存，
  提醒里就会写「暂时缺货」——和降价提醒踩的是同一个坑。
- **召回幂等靠 `(username, source_key)` 唯一索引**（实测 H2 允许多行 NULL，故普通提醒不受影响），
  只召回 TIMEOUT、**不召回 USER**（主动取消是「不想买了」，再推荐是打扰）。
- **扫描不照抄游标**：到期订单被关掉后离开结果集，队列天然收敛。

## 本轮踩到的两个坑（都很值得记）

1. **对 spy 的 `MANDATORY` 事务方法设桩 → 桩只设了一半，并污染了同一个 spy 的后续状态。**
   `doThrow(...).when(catalog).release(...)` 里 `release` 标了
   `@Transactional(propagation=MANDATORY)`，事务代理先把它挡下 → stubbing 中断 →
   **另一个用例里同一个 spy 的 `get()` 静默返回 `null`**（症状离根因很远，是 NPE）。
   修法：把设桩包进 `TransactionTemplate`，先满足 MANDATORY。
2. **反向验证第一次是「全绿」的**——说明测试有盲区，不是设计没问题。
   已支付订单根本不进扫描候选集，所以扫描路径的测试碰不到「关单动作自身的前置条件」。
   补了两个绕过扫描、直接调 `closeExpired(id, now)` 的用例后才变红（`Failures: 2`）。
   教训：**反问自己「这条断言在旧实现下会不会红」，答案是「不确定」就说明它在测别的东西。**

## 验证

- 反向验证两轮：去掉条件更新 → `Failures: 2`；让主动取消也发召回事件 → `Failures: 1`。
- 真机（真实 Tomcat + 文件库，支付时限压到 1 分钟）：
  V10/V11 迁移成功；冒烟 `tests/order-expiry-smoke.cjs` **12/12 通过**

## 顺手修掉了技能里一个会主动误导人的 bug

`context-mode` 的日志级别统计用 `if level in line.upper()` 做**子串**匹配，
于是 Maven 的 `Errors: 0`（**零失败**）被算成 25 条 ERROR，
压缩摘要给出「发现 25 条错误/致命日志」——**与事实完全相反**（真实 ERROR 行数为 0）。
已改为词边界匹配 `(?<![A-Z])level(?![A-Z])` 并复跑 `--selftest` 全绿。
**教训：压缩工具的产物如果自己会说谎，那压缩后的信息比不压缩更危险。**
（另记：该技能 `scripts/` 下 `run.py` 与 `main.py` 内容完全重复，同 20642 字节，属冗余未清理。）

**给 `@EventListener` 加 `@Transactional` 会让 `OrderExpiryTest` 变红**

**同步事件天然与发布方同线程同事务，不需要监听方加事务注解。**
