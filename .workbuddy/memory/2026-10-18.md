## 内置钱包（用户提的新需求，方案已出）

**关键发现**：`DemoWalletPayment` 早就是空壳——`pay()` 只 `return "SIM-WALLET-" + orderId`，不查余额、不扣款、不落账。数据库里根本没有余额概念。所以不是从零建，是把假实现补成真的。

方案落盘 `docs/内置钱包设计方案.md`（774 行），退款方案追加 §13 交叉引用。核心结论：

| 问题 | 结论 |
| --- | --- |
| 余额类型 | **BIGINT 分**；元→分唯一落点 `MoneyUnits.toCents`（scale>2 直接抛，绝不四舍五入）+ 源码扫描测试 |
| 流水表 | `wallet_ledger` 照 `stock_ledger` 形状，另加 PAYMENT 必须负 / REFUND 必须正的**方向约束** |
| 并发 | 条件 UPDATE **+ 行锁**，缺一不可 |
| 迁移 | **钱包 V16、退款顺延 V17**（后经追加决定改正：先落钱包）；**两个文件必须同一次提交落盘**（Flyway 默认禁 out-of-order） |

**架构师推翻我的三处**（都要记住）：
1. 挡住并发超扣的是**行锁**，不是条件 UPDATE。无行锁时最终余额是对的、对账恒等式也成立（`after` 是 Java 用同一个 `before` 算出来的，恒真），**只有「相邻流水首尾相接」的窗口查询能抓住**。所以「断言最终余额正确」守不住行锁，已被单列为对照组并标注「非证据」。
2. 顺带更正 `StockLedgerTest` 的既有注释：它声称漏行锁时 `ck_ledger_arithmetic` 会抛错——按同一推导抓不到（结论不变，理由要换）。
3. 初始额度**不放迁移**（迁移读不到 yml，写死就是第二个真相来源）→ 改配置 `mall.wallet.initial-grant-cents` + 懒开户。

**会架空方案的前提**：DEMO_CARD 支付的订单退款时依然没有真实放款（钱本就没进钱包），而**助手代付默认就是 DEMO_CARD**。处置待用户拍板：默认支付方式切成 DEMO_WALLET。

## 本轮新增的四条硬教训

### 4. 派工报 `name already in use` ≠ 没启动
工具返回这个名字冲突错误时，**进程其实已经跑起来了**，只是名字注册失败。我误判成"没启动"又换名重派，导致两个 agent 在同一工作树改同一批文件（互相覆盖、`WalletLedgerEntry` 被冲掉一次、两次 30 分钟空转）。**正确动作：先确认进程是否存活，不要换名字再来一次。**

### 5. 两个 maven 并发跑同一 `target/` 会制造假红
一个 maven 重写 `target/classes` 时，另一个会报 90 条 `Unable to find a @SpringBootConfiguration`（上下文被掏空）。T19 那次 399/4/90 就是这个，**不是真失败**。另外单跑 maven 只要 1m22s，卡 30 分钟全是并发造成的。
→ **一棵工作树必须串行使用；要并行就各开独立工作树。**

### 6. 前端「接口通了但用户看不见」单测抓不到
`index.html` 里钱包条是 `<div id="wallet" class="wallet-strip hidden">`，`.hidden` 是 `display:none !important`，而 `renderWallet()` 只赋 `innerHTML`、**从不摘 `hidden`**。结果接口全绿、数据到位，页面上一个字都没有——和"接口根本没通"长得一模一样。**只有真跑起来才看得见。**

### 7. 文档里可能埋着「兑现不了的承诺」
`AssistantActor.capabilityHint()` 的 merchant 分支写着「退款审批功能尚未开放，在工具就绪前不要向买家承诺可以处理退款」。T13b 落地后这句就成了**假话**，而模型会照着它继续拒绝。**凡是"功能未开放"这类文案，功能上线时必须回头删。**

## 两条新教训

### 8. 「半成功」有两侧，只验一侧会假绿
`NotificationSink` 里 `.param("content", event.content())` 出现**两处**（站内信 + 留痕）。变异脚本截断站内信那侧时，只断言留痕的用例**全绿**——补上两侧断言后才红。
危险在于：**截断恰恰是看到 `Value too long` 后最顺手的错误修法**——报错消失了，代价是正文被砍掉一截，而这在功能上完全不可见。
同类：`notification.content` 是 VARCHAR(500) 而 `notification_delivery.content` 是 VARCHAR(400)，长度不对称会在文案超长时制造半成功。已开 **V19** 对齐；断言写的是「两列**相等**」而不是写死 500——写死会在将来又一次单边改动时失效。

### 9. 断言「相等」比断言具体值更能守住不变量，但要补下限
只断言两侧相等有个洞：一起被压到 50 也会绿。所以还要加一条下限（≥500）——把上限往下调属于「改需求」，得有人显式来改那条断言。
