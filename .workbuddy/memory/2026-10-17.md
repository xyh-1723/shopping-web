### 独立核验：架构师「风险最高项」可被消除

架构师在 `docs/退款与履约设计方案.md` 断定「H2 2.3.232 不支持条件唯一索引，
所以『一笔订单只能有一笔在途退款』只能靠每个入口记得 `SELECT ... FOR UPDATE`，漏一个＝静默双退款」。

实测（H2 2.3.232 + jdk-18 单文件模式）：
- 条件唯一索引确实报 `Syntax error` → **架构师这条没说错**；
- 但**生成列 + 唯一索引可行**：

```sql
in_flight VARCHAR(36) GENERATED ALWAYS AS
  (CASE WHEN status IN ('REQUESTED','APPROVING') THEN order_id END)
CREATE UNIQUE INDEX uk_refund_inflight ON refund(in_flight)
```

六条探针全过：同一订单第二笔在途**被拒**；终态允许多行（历史可留多条）；
不同订单互不影响；**UPDATE 后生成列正确重算**（`REFUNDED` → NULL）；
退款完成后**可再申请一笔**（约束没退化成永久封禁）。

最后两条是特意补验的——若生成列不重算，约束就会从「防重复」变成「永久封禁」，方案即假。
探针：`artifacts/rev-check/PartialUniqueProbe.java`、`GeneratedColumnRecomputeProbe.java`。

→ 已派架构师修订方案：把该约束从「应用层纪律」提升为「数据库保证」，
并重新设计 T14 的反向验证（不能再靠"去掉 FOR UPDATE"变红，DB 层会顶住）。

## 修掉最后一个 flake：AssistantStreamTest.streamEndpointReportsFailureAsEvent

### 我上一轮的定性是错的（值得记住）
我把它记成「MockMvc 异步 10s 超时」。实测 20 轮里 5 次红：3 次 15ms 就红、2 次 10s 超时。
**同一根因的两种外观** —— 只看一次失败就把现象当结论，差点把修法带到「加大超时」那条错路上。

### 真根因：两条线程并发写同一个非线程安全的响应头表
`MockHttpServletResponse` 的头表 = `LinkedCaseInsensitiveMap` 包着**普通 `LinkedHashMap`**。
SSE 端点把轮次提交给线程池后：
- **worker 线程** flush 事件 → `ServletServerHttpResponse.writeHeaders()` → `addHeader()`
- **请求线程** handler 返回后 filter 链收尾 → `HeaderWriterFilter.doHeadersAfter` → `setHeader()`

两个窗口几乎重合 → `HashMap.computeIfAbsent` 抛 `ConcurrentModificationException`。
- CME 落在**请求线程**：直接从 `mvc.perform(...)` 抛出 → 15ms 红；
- CME 落在 **worker 线程**：被 `TurnStreamSink.emit` 的 `catch` 吞掉并置「已关闭」标记 →
  `close()` 不再调用 `emitter.complete()` → 异步结果永远不来 → **10s 超时**。

**一致性佐证**：`/messages` 用 `Callable`，worker 体内不碰响应对象（响应在 async dispatch 时才写），
所以从不红；只有 `/stream`（SSE 每 flush 一次就写头）会红。模型与观察完全对上。

**不是端点缺陷**：真实容器里响应在首次 flush 即提交，安全头由 `OnCommittedResponseWrapper`
在那一刻由同一条 worker 线程写出，无跨线程竞争。故 `src/main` 零改动。

### 修法（不是加大超时）
本测试类把 `assistantTurnExecutor` 换成 `DeferredTurnExecutor`：`execute` 先攒着，
等请求线程把 filter 链走完（安全响应头此时已写完），再由测试显式 `drainAndAwait()`
放行到**真实线程池**并等到轮次真的跑完。两条线程不再重叠 → 竞争的结构性前提消失。
轮次依旧跑在真实线程池上，「不占用 Tomcat 工作线程」这条生产属性仍被覆盖
（装配断言在 `AssistantConcurrencyTest:340`）。断言语义一字未改。

注：`ThreadPoolTaskExecutor.submit(Runnable)` 直接调 `getThreadPoolExecutor().submit()`，
不走 `execute()`，所以 `Callable` 路径不受本次覆盖影响（改动面被限制在 SSE 一处）。

### ⚠️ 最重要的发现：SecurityConfig 那段改动是 no-op
第 4b（撤掉 `OrRequestMatcher` 的 `/actuator/**`）**完全不变红**。不是测试写错，是**改动本身不改变行为**：

**根因**：Spring Security `ExceptionHandlingConfigurer.createDefaultEntryPoint()`
——当 `defaultEntryPointMappings` **只有 1 条**时，直接把该 entry point 当全局默认返回，
**完全不看 matcher**；只有 ≥2 条才走 `DelegatingAuthenticationEntryPoint`。
→ 即 `/actuator/**` 在这次改动**之前**就已是 401。`OrRequestMatcher` 那行是空操作。
实证：撤成只剩 `/api/**` 后，匿名访问 `/cart`、`/orders`、`/some/unknown/path` 仍全部 401。

**处置**：保留该行（将来若加第二个 `defaultAuthenticationEntryPointFor`，delegation 才生效，
属显式防御），但**注释必须改**——原文「把 /actuator 的 401 JSON 入口扩展过去」与实测不符，会误导后人。
另：该断言实际守的是**授权规则**（4c 证明），不是入口改写，文档也要订正。

### 两处覆盖缺口（已派 QA 补）
- **#6** Gauge「不扫描就保留上轮值」→ 反转成 `set(0)` 后 302 全绿，**无测试守**。
  危险：删掉后「排障中没人扫」会被伪装成「积压为 0」，把故障静默隐藏。
- **#7** DUPLICATE 短路记成 `STATUS_OK` → 302 全绿，**无测试守**。
  危险：短路/超时同样是「模型以为拿到了其实没有」，不统计会让失败率凭空变好看。
